# DBTower 5분 시연 순서

면접·발표에서 화면을 직접 보여 줄 때의 순서다. 한 흐름(느린 쿼리 발견 -> 인덱스 변경 요청 -> 승인 -> 실행 -> 전후 확인)을 역할을 바꿔 가며 끝까지 보여 주고,
남는 시간에 테이블 보기를 붙인다. 각 장면의 근거 수치는 [VERIFICATION](VERIFICATION.md) 절 번호로 적었다. 네트워크나 AI가 느리면 [데모 GIF](images/demo-change-flow-glass.gif)로 대신한다.

처음 환경을 준비하거나 역할별 버튼을 차례로 확인하려면
[역할별 수동 테스트](MANUAL-TEST.md)를 먼저 따른다.

## 시연 전 준비 (5분 전)

- `docker compose up -d`로 대상 DB와 모니터링 스택을 띄우고 앱을 켠다([README 셀프호스트](../README.md)). 대상은 PostgreSQL 인스턴스 하나면 된다
- 관리자 화면에서 요청자·승인자·운영자 계정을 하나씩 만든다(사용자·역할 카드). 브라우저는 창 셋을 서로 다른 프로필(또는 시크릿 창)로 열어 각자 로그인해 둔다
- 요청자 창에서 관제 모드 PostgreSQL을 열어, Top Query 표에 `ORDER BY created_at` 조회가 보이는지 확인한다(부하가 없으면 표가 비어 있다).
  **1위가 사용자 쿼리가 아닐 수 있다** — 대상이 한가하면 플랫폼 자신의 감시 조회와 함께 띄운 postgres-exporter의 조회가 상위를 차지한다(161절 실측: 감시 계정 38.4%).
  보여 줄 행은 2~3위에 있을 수 있으니 미리 위치를 확인해 두고, 질문이 나오면 "관측 비용을 숨기지 않는다"로 답한다
- 서비스 토큰이 찍히는 관리자 대시보드의 MCP 카드는 화면 공유에 띄우지 않는다

## 순서

| 시간 | 창(역할) | 누를 곳 | 말할 것 |
|---|---|---|---|
| 0:00 - 0:30 | 없음 | [한 장 요약](PORTFOLIO-ONEPAGER.md)의 "풀려는 문제" | DB 이슈가 나면 개발자는 기종마다 흩어진 지표를 오가다 DBA에게 묻고, 변경은 DB 클라이언트에서 따로 실행돼 증거가 남지 않는다. 이걸 한 플랫폼의 역할별 입구로 푼다 |
| 0:30 - 1:30 | 요청자 | 상단 [관제] -> PostgreSQL -> Top Query 행 -> 쿼리 상세의 실행계획 보기·AI 분석·관련 테이블 구조 | 실행계획은 AI를 기다리지 않고 먼저 보인다(143절 38~39초 -> 0.02~0.05초). AI는 판단자가 아니라 사람이 정한 규칙 문서 위의 1차 분석기다. 관련 테이블 구조에 기본키·외래키가 같이 나온다(151절) |
| 1:30 - 2:15 | 요청자 | 인덱스 제안 -> 열 입력 -> 가상 인덱스 비용 -> "워크벤치에서 변경 요청으로 올리기" | HypoPG 가상 인덱스라 실제로 만들지 않고 Total Cost 전후만 본다(137절). 버튼은 새 탭이 아니라 같은 페이지의 워크벤치 모드로 넘긴다(149절) |
| 2:15 - 2:45 | 요청자 | 변경 요청 창에서 요청 올리기 | 규칙 판정(락 위험·스키마 대조)이 먼저 뜨고 AI 1차 소견은 쓰이는 대로 이어진다(146절). 요청자는 여기까지만 할 수 있다 |
| 2:45 - 3:30 | 승인자 | 상단 [워크벤치] -> 가운데 "변경 티켓" 탭(열린 것만 먼저, 152절) -> 티켓 -> 드라이런 -> 승인 | 드라이런은 실제로 실행하고 롤백해 바뀔 행과 계획을 본다. 승인자에게는 실행 버튼이 없다. 승인과 실행은 다른 사람이다(135절, 실행 시도 403) |
| 3:30 - 4:20 | 운영자 | 같은 티켓 -> 실행(버튼이 "실행 확인(한 번 더)"로 바뀌면 다시) -> 실행 기록의 구조 변화·검증 조회 계획 전후 -> "실행 전후 워크로드 비교(60분)" | 실행권은 `status = 'APPROVED'` 조건부 UPDATE로 한 요청만 얻는다. 안전은 SQL 파싱이 아니라 사본 행 수와 영향 행 수가 같을 때만 커밋하는 불변식에서 나온다(130절) |
| 4:20 - 5:00 | 운영자 | 워크벤치 왼쪽 스키마 트리 -> orders "상세" -> 외래키 표 -> customers 링크 | 기본키·외래키를 5기종 카탈로그에서 같은 모델로 읽는다. 이 데모 외래키도 승인 티켓으로 올렸는데, MySQL·SQL Server에서 변경 계정에 REFERENCES 권한이 없어 실행이 거부됐다. 최소 권한이 실제로 막은 사례다(151절) |

## 질문이 오면 바로 열 곳

| 질문 | 열 곳 |
|---|---|
| 승인된 SQL과 실행된 SQL이 같다는 증거는 | 티켓 상세의 실행 기록(문장 SHA-256·영향 행 수·사본), 130절 |
| AI가 틀리면 | 판단 기준 문서 `docs/ai-analysis-rules.md`, AI에는 실행 도구가 없다(129절) |
| 대상 DB가 죽으면 플랫폼도 멈추나 | 134절: 연결만 받고 말이 없는 대상 하나가 모든 폴러를 세우던 결함과 재현 테스트 |
| 보는 사람이 늘면 대상 DB 조회도 느나 | 140·144절: 서버 허브, 10명 기준 150회 -> 14회 |
| 새 DBMS를 붙이려면 | `DbmsOperator` 구현체 1개가 본체, 나머지는 등록 절차(README "확장성 증명") |

## 끝낸 뒤

- 데모로 만든 인덱스는 운영자의 역변경 제안("역변경 티켓으로 올리기")으로 지운다. DDL은 행 사본으로 되돌리지 않는다.
  올린 역변경 티켓도 승인·실행을 다시 거친다 — 되돌리기조차 같은 게이트를 지난다는 것을 보여 줄 마지막 기회다
- 더 깊은 질문은 [면접 예상 질문](INTERVIEW-QA.md)과 [PORTFOLIO-AX](PORTFOLIO-AX.md)의 사례로 이어 간다
