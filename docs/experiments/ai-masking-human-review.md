# E2 원문 판정: 마스킹 토글이 가리는 것과 AI 진단 정확도

`ai-masking-tradeoff.md` 는 실험 테스트가 실행마다 다시 만드는 문서라 자동 채점만 담는다.
이 문서는 `ai-masking-responses.jsonl` 의 응답 원문 36개를 읽고 판정한 결과다(2026-09-17). 판정자는 사람이 아니라 실험을 진행한 AI 코딩 세션이다.

> **정정(`ai-masking-repeat-review.md`).** 반복 실험에서 기준을 좁혀 L4(깊은 OFFSET)와 L6(낮은 선택도)을 모든 조건에서 ✓에서 △로 고쳤다. AI가 두 사례 모두 "판정할 수 없다"고 답했기 때문이다. 아래 표는 처음 판정 그대로 둔다.

## 무엇을 쟀나

AI SQL 진단(`AiAnalysisRunner`)의 프롬프트는 SQL, 실행계획, 규칙 기반 지적으로 이루어진다.
`mask-ai-prompt` 토글은 **SQL 문장만** 가린다. 세 조건으로 비교했다.

| 조건 | SQL | 실행계획 |
|---|---|---|
| A | 원문 | 원문 (현재 기본값) |
| B | 가림 | 원문 (토글을 켰을 때의 실제 동작) |
| C | 가림 | 작은따옴표 문자열 리터럴만 가림 |

모델은 `claude-opus-4-8`(claude CLI 모드), 사례 12개 × 조건 3개 = 36회, 사례마다 1회 호출이다. 호출 오류는 0건이다.

## 노출: 프롬프트에 남은 민감 리터럴 원값

프롬프트 원문에서 다시 세어 확인했다.

| 조건 | 남은 원값 | 어디서 |
|---|---|---|
| A | 31 | SQL과 실행계획 |
| B | 14 | **전부 실행계획.** PostgreSQL은 `Filter`·`Index Cond` 에 값이 그대로 찍히고, `IN` 목록은 `= ANY('{1,...,500}')` 배열로 통째로 남는다. MySQL은 `attached_condition` 에 조건 값이 남는다 |
| C | 1 | MySQL L1. 문자열 열에 숫자 리터럴을 비교하면 계획이 값을 따옴표 없는 숫자(`phone = 1012345678`)로 찍어 문자열 마스킹에 걸리지 않는다 |

**토글을 켜도 노출은 절반 남짓(31 → 14)만 줄었고, 남은 값은 모두 실행계획을 타고 AI로 갔다.**

## 정확도: 응답 원문 판정

✓ 정답 원인을 원인으로 지목 / △ 후보로만 언급하고 확정하지 못함 / ✗ 지목 못 함

| 사례 | 기종 | 기대 원인 | A | B | C | 비고 |
|---|---|---|---|---|---|---|
| L1 | MySQL | 암시적 형변환 | ✓ | ✓ | ✓ | |
| L2 | MySQL | 앞 와일드카드 | ✓ | ✓ | △ | C: 계획의 패턴이 `'?'` 라 "확정할 수 없다" |
| L3 | MySQL | 낮은 선택도 | ✓ | ✓ | ✓ | 사례 오류: 기대는 풀스캔이었으나 계획은 인덱스 `ref`. AI는 "돌려주는 행(99,852)이 많은 것이 원인"으로 선택도를 짚음 |
| L4 | MySQL | 깊은 OFFSET | ✓ | ✓ | ✓ | 판단 기준 문서에 OFFSET 규칙은 없지만 190,020행을 훑는 구조를 부담으로 지목 |
| L5 | PostgreSQL | 앞 와일드카드 | ✓ | ✓ | ✗ | C: 가려진 `'?'::text` 를 "자리표시자로 EXPLAIN을 돌린 것"으로 오독하고 원인 확정 실패 |
| L6 | PostgreSQL | 낮은 선택도 | ✓ | ✓ | ✓ | |
| L7 | PostgreSQL | IN 목록 과다 | 제외 | 제외 | 제외 | **사례 오류.** 500개 IN이 기본키 `Index Only Scan` 으로 처리돼 실제 비효율이 없다. AI의 "신호 없음"이 맞다 |
| L8 | PostgreSQL | 낮은 선택도(전 행) | ✓ | ✓ | ✓ | |
| C1 | MySQL | 컬럼에 함수 | ✓ | ✓ | ✓ | 대조군 |
| C2 | MySQL | 복합 인덱스 선두 누락 | ✓ | ✓ | ✓ | 대조군 |
| C3 | PostgreSQL | 컬럼에 함수 | ✓ | ✓ | ✓ | 대조군 |
| C4 | PostgreSQL | 조인 키 인덱스 없음 | 제외 | 제외 | 제외 | **사례 오류.** 실제 계획이 Hash Join이라 조인 키 인덱스 부재가 드러나지 않는 모양이다. B는 `orders.customer_id` 인덱스 검토를 제안했다 |

유효 사례 10개(리터럴 의존 7, 대조군 3) 기준:

| 조건 | 리터럴 의존 (7) | 대조군 (3) |
|---|---|---|
| A | 7 | 3 |
| B | 7 | 3 |
| C | 5 (+△ 1) | 3 |

## 결론

1. **토글(B)의 정확도 대가는 이 사례 세트에서 관측되지 않았다.** A와 B가 같다. 반면 토글이 약속한 보호도 절반만 이뤄졌다. 값이 실행계획으로 샌다
2. **계획까지 가리면(C) 노출은 31 → 1로 줄지만, 앞 와일드카드 두 사례에서 AI가 원인을 확정하지 못했다.** 가려진 패턴만으로는 `'%x'` 와 `'x%'` 를 구분할 수 없기 때문이다. 이것이 실제로 관측된 개인정보 보호와 진단 정확도의 교환이다
3. 대조군은 세 조건에서 모두 같아, 조건 차이가 실험 장치 때문에 생겼다는 신호는 없다

## 한계

- 사례 12개 중 2개(L7, C4)는 기대 원인을 잘못 설계해 제외했고, 1개(L3)는 계획 모양이 기대와 달랐다
- 사례마다 1회 호출이라 같은 조건의 응답 편차를 재지 않았다
- 실행계획은 제품 경로 그대로 MySQL `EXPLAIN FORMAT=JSON`, PostgreSQL `EXPLAIN (FORMAT JSON)` 이다
- C의 계획 마스킹은 실험에서만 구현했다. 제품 코드는 바꾸지 않았다
