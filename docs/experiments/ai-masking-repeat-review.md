# E2' 반복 판정: 가림 조건별 AI 진단 (2026-09-17)

`ai-masking-repeat.jsonl`(반복 응답 70건)과 E2 1회차 응답을 **이 AI 코딩 세션이 원문을 읽고** 판정한 결과다.
E2 문서(`ai-masking-human-review.md`)의 판정도 사람이 아니라 같은 세션이 한 것이다. 이 문서에서 기준을 좁혀 1회차 판정 일부를 고쳤다.

## 조건

| 조건 | SQL | 실행계획 |
|---|---|---|
| A | 원문 | 원문 (제품 기본값, 1회만) |
| B | 가림 | 원문 (가림 설정을 켰을 때의 실제 동작) |
| C | 가림 | 작은따옴표 문자열 값을 전부 `'?'` |
| D | 가림 | 문자열 값은 지우고 앞뒤 `%` 자리만 남김 (`'%@gmail.com'` → `'%?'`) |

- 사례: E2의 12개 중 설계 오류 L7·C4를 뺀 10개. B·C는 1회차 + 반복 2회, D는 3회
- 모델 호출은 제품 `AiAnalyzer`의 claude CLI 모드다. CLI 모드는 모델을 지정하지 않아 CLI 기본 모델로 돈다(E2 jsonl의 `model` 값은 코드 상수라 실제 모델을 뜻하지 않는다)
- 매 실행이 실험 테이블을 다시 만들고 실행계획을 다시 뜨므로 추정 행수 같은 숫자는 회차마다 조금씩 다르다. 값을 가리는 모양은 같다

## 노출: 프롬프트에 남은 민감한 값 (유효 사례 10개)

| A | B | C | D |
|---|---|---|---|
| 23 | 10 | 1 | 1 |

C와 D에 남은 1은 L1이다. MySQL이 문자열 열과 비교한 숫자를 따옴표 없이 계획에 찍어 문자열 가림에 걸리지 않는다.

## 판정 기준 (1회차부터 다시 적용)

- ✓ 기대 원인 쪽으로 결론을 냈다 ("가장 유력한 원인은 ...", "... 가능성이 크다")
- △ 기대 원인을 후보로만 들거나 원인 판정 자체에 "판정할 수 없다", "확인할 수 없다"를 붙였다
- ✗ 기대 원인을 들지 않았다

**1회차에서 고친 판정**: L4(깊은 OFFSET)는 모든 조건에서 AI가 "판단 기준 문서에 OFFSET 규칙이 없어 판정하지 않는다"고 답했다. 1회차에는 A·B·C를 ✓로 봤지만 △가 맞다. L6(낮은 선택도)도 모든 조건에서 "테이블 전체 행수가 없어 판정할 수 없다"였다. ✓를 △로 고쳤다. L2의 C1은 "가장 유력하지만 확정할 수 없다"라 1회차 판정 △를 그대로 둔다. L3는 계획 모양이 설계와 달라(풀스캔 기대, 실제 인덱스 조회) 정확도 집계에서 뺀다.

## 집계

값이 진단을 가를 수 있는 사례 5개(L1, L2, L5, L6, L8) × 3회:

| 조건 | 노출 | ✓ | 세 번 모두 같은 판정이었나 |
|---|---|---|---|
| A | 23 | 4/5 (1회) | - |
| B | 10 | 12/15 | 사례마다 세 번 같음 |
| C | 1 | 3/15 | 사례마다 세 번 같음 (L5만 ✗ 1, △ 2) |
| D | 1 | 9/15 | 사례마다 세 번 같음 |

대조군 3개는 B·C·D 모두 9/9. L4·L6은 모든 조건에서 △라 조건 차이를 보여 주지 않는다.

## 읽은 것

1. **반복해도 판정이 흔들리지 않았다.** 조건이 같으면 사례마다 세 번 같은 판정이었다(C의 L5에서 ✗와 △가 갈린 한 건 제외). 1회차의 차이가 우연이 아니었다
2. **D는 와일드카드 두 사례를 되살렸다.** C에서 △·✗였던 L2·L5가 D에서 세 번 모두 ✓다. `%` 위치만 있으면 값 없이도 원인을 짚었다. 노출은 C와 같은 1이다
3. **D도 L8은 되살리지 못했다.** `created_at >= '2000-01-01'`의 값이 "거의 전 기간"이라는 정보였고, `'?'`로 가리면 선택도를 판단할 근거가 사라졌다. 값의 모양이 아니라 값 자체가 근거인 경우다
4. **B(지금 설정)는 정확도를 거의 잃지 않지만 보호도 절반 수준이다.** 노출 23 → 10

## 판정기를 쓰지 않은 이유

claude CLI 판정기(`judge_masking.py`)를 1회차 판정과 먼저 대조했다. 사용 한도에 걸리기 전 판정한 22건 중 일치 9건이었다. 판정기는 조건을 달아 말한 답을 대부분 "후보"로 봤다. 기준이 이 문서와 달라 판정에 쓰지 않았다. 판정기 출력은 `ai-masking-judge-calibration.jsonl`에 남겼다.

## 한계

- 사례 5개 × 3회는 작다. "B는 정확도를 잃지 않는다"는 이 사례들에서의 관찰이다
- 판정자가 한 명(이 세션)이고 독립 판정자와 대조하지 못했다
- D는 실험에서만 구현했다. 제품 코드는 바꾸지 않았다

## 조건 E — 제품 가림 함수 (2026-09-18 추가)

조건 D까지는 실험 장치였다. 조건 E는 제품 `PlanMasker.maskPlan`을 그대로 불러 만든 프롬프트다.
D와 다른 점은 **숫자까지 가린다**는 것이다 — C·D는 작은따옴표 문자열만 봐서 계획에 맨숫자로 찍힌 값
(L9의 `99000`, L1의 전화번호)이 남았다.

사례는 15개 중 설계 오류인 L7·C4를 뺀 13개, 각 3회로 39건이다.

| L2 | 앞 와일드카드 (MySQL) | ✓ ✓ ✓ |
| L3 | 낮은 선택도 | △ ✓ △ |

| L5 | 앞 와일드카드 (PostgreSQL) | ✓ ✓ ✓ |

L3는 계획 모양이 설계와 달라(풀스캔 기대, 실제 인덱스 조회) 1회차부터 집계에서 뺐다.

L4·L6은 모든 조건에서 △라 조건 차이를 보여 주지 않는다.

### 읽은 것

1. **숫자까지 가려도 진단이 살아남았다.** 조건 E에서 노출은 0인데, 조건 차이를 보여 주는 사례
   (L1·L2·L5·L9·L11과 대조군 셋)는 아홉 번 모두 ✓다. 값이 아니라 **구조**가 진단의 근거라는 뜻이다.
   L1이 특히 분명하다 — 비교값이 `?`로 가려졌는데도 `possible_keys`에 인덱스가 있고 `access_type=ALL`이라는
   사실만으로 암시적 형변환을 짚었다
2. **D가 되살린 와일드카드는 E에서도 유지된다.** `'%?'`의 `%`만 남으면 충분하다
3. **L8은 E에서도 되살아나지 않는다.** 값의 모양이 아니라 값 자체가 근거인 경우다(D와 같은 한계)
4. **가림이 남긴 새 불확실성이 응답에 드러났다.** L5의 한 회차가 "그 `%`가 원본 패턴의 선두인지
   가림 처리가 남긴 문자인지는 계획 텍스트만으로 확정할 수 없다"고 적었다. 판정은 맞았지만,
   모델이 **가려진 자리를 인지하고 그만큼 조심**한다는 신호다. 이 부작용은 앞으로도 남는다
