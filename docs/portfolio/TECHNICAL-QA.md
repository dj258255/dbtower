# DBTower 기술 질문과 답

핵심 설계 결정을 질문과 답으로 빠르게 찾는 문서다. 답은 짧게, 근거는 절 번호로 붙인다.
수치는 [VERIFICATION](../verify/VERIFICATION.md)에 명령·출력 원문이 있는 것만 쓴다.

## 설계

**Q. 관제 대시보드와 SQL 워크벤치를 왜 한 제품으로 두었나요?**
두 화면이 인스턴스 등록, 팀 범위, 감사, 변경 티켓, AI 진단을 공유하기 때문입니다. 운영자는 관제에서 이상을 보고, 워크벤치에서 데이터로 확인하고, 변경을 올리고,
실행 뒤 다시 관제에서 전후를 봅니다. 제품을 나누면 이 흐름이 시스템 경계를 넘어 인증·범위·감사를 두 번 맞춰야 합니다. 대신 역할을 다섯으로 나눠 사람마다 첫 화면과 버튼을 다르게 했습니다(135절).

**Q. 승인자와 운영자를 왜 따로 두었나요? 자기 승인 금지 설정으로 충분하지 않나요?**
자기 승인 금지는 요청자와 승인자의 이름이 같은지만 봅니다. 역할이 ADMIN 하나였을 때는 승인한 사람이 곧바로 실행할 수 있었습니다. 승인자와 운영자가 서로를 포함하지 않는
역할 계층으로 두면 설정과 무관하게 승인과 실행이 다른 사람에게 갑니다. 라이브에서 승인자의 실행 시도는 필터에서 403이었습니다(135절).

**Q. 워크벤치 배치를 왜 다시 갈아엎었나요?**
처음에는 오른쪽 탭 하나에 채팅·스키마·변경 티켓을 같이 넣었습니다. 모양은 참고 제품과 비슷했지만 역할은 달랐습니다. 스키마는 사람이 대상을 고르는 길잡이라 채팅과
함께 보여야 하고, 티켓 상세는 넓은 가운데 작업면에서 읽어야 했습니다. 배치를 바꾼 뒤 스키마의 orders를 질문에 붙이는 흐름은 클릭 4회에서 2회로 줄었고,
티켓 상세 칸은 398px에서 524px로 넓어졌습니다(147절).

**Q. 관제와 워크벤치를 한 페이지의 두 모드로 만든 이유는요?**
관제 쿼리 상세에서 워크벤치로 넘길 때 새 탭을 열면 두 화면이 같은 상태를 나눠 가지기 어렵고, 숨은 화면의 실시간 연결도 남습니다. 한 페이지의 [관제 | 워크벤치] 모드로 바꿔
탭 2개를 1개로, 문서 로드를 1회에서 0회로 줄이고, 안 보이는 모드의 실시간 연결을 닫게 했습니다(149절).

**Q. 5종 DBMS의 차이는 어디에 숨겼나요?**
플랫폼 코드는 `DbmsOperator` 인터페이스에만 의존하고, 기종별 구현 선택은 팩토리 한 곳에만 둡니다. 다른 곳에서 기종으로 분기하는 코드가 늘지 않게 기준선을 규약 검사로 빌드에 넣었습니다.
같은 "읽은 행 수"도 MySQL은 검사한 행, PostgreSQL은 돌려준 행, SQL Server는 논리 읽기 페이지라, 그 뜻은 기종 오퍼레이터가 답하게 인터페이스에 넣었습니다(132절).

**Q. 이런 관제 플랫폼이면 로그 파일이나 시계열 DB에 쌓는 게 보통 아닌가요? 왜 PostgreSQL입니까?**
데이터 종류마다 다릅니다. 넷으로 나눠 각각 맞는 곳에 둡니다.

리소스 메트릭(CPU·메모리·커넥션·디스크)은 **Prometheus**가 맡습니다 — `node-exporter`, `mysqld-exporter`,
`postgres-exporter`와 앱 자신을 긁고 Grafana가 봅니다. 애플리케이션 로그는 stdout입니다.

PostgreSQL에 두는 것은 **상태·설정, 증거 기록, 그리고 고카디널리티 시계열** 셋입니다.
`query_snapshot`을 Prometheus로 옮기지 않는 이유가 이 구분을 잘 보여 줍니다 — `query_id`는 인스턴스마다
수천 종이고 계속 바뀌어 라벨로 넣으면 시계열이 쿼리 수만큼 생깁니다(전형적인 카디널리티 폭발).
게다가 Prometheus는 숫자만 담아 `query_text` 4000자를 실을 자리가 없는데, "어제와 비교해 느려진 쿼리의
SQL을 보여 줘"가 제품의 핵심 기능입니다.

**Q. 그러면 append-only 로그 파일로는 왜 안 되나요?**
실행권을 주는 것이 조건부 UPDATE이기 때문입니다.

```java
@Query("update ReviewRequest r set r.status = :to where r.id = :id and r.status = :from")
int transition(Long id, Status from, Status to);
```

운영자 둘이 같은 티켓의 실행 버튼을 동시에 눌러도 바뀐 행 수가 1인 쪽만 실행권을 얻습니다.
파일에 append하고 나중에 읽어 판단하면 **읽는 순간과 쓰는 순간 사이에 남이 끼어듭니다.**
파일 잠금으로 흉내 내려면 결국 DB를 다시 만드는 셈이 됩니다.

**Q. 그러면 시계열 데이터를 DB에 넣는 대가는 어떻게 치렀나요?**
로그 파일의 장점(버리기 쉬움)을 파티션으로 가져왔습니다. 오래된 구간을 행 단위로 DELETE하지 않고
`DROP TABLE`로 통째로 떼어 냅니다 — `logrotate`와 같은 일입니다(V18 실측: 200만 행 DELETE 1.9초,
VACUUM 후에도 공간 미반환).

파티션 단위는 표마다 다릅니다. **같은 규칙이 아니라 같은 기준을 적용합니다** — 최악 상주 행수입니다.
`query_snapshot`은 하루 72만 행이라 월 파티션의 최악 상주가 2,664만 행으로 감당되지만,
`ash_sample`은 1초 주기라 하루 216만 행이어서 월로 하면 7일 보존인데 최악 37일치(7,992만 행)를
들고 있게 됩니다. 그래서 이쪽만 일 단위입니다(201절).

**Q. 셀프호스트인데 저장소를 하나로 두면 나중에 부담 아닌가요?**
규모가 커지면 분리가 이깁니다. 다만 **셀프호스트일수록 부품 수가 비용**입니다 — 저장소를 하나 더 두면
설치하는 사람이 백업·업그레이드·장애 지점을 둘 관리하게 됩니다. 상용 제품도 갈립니다. pganalyze는
PostgreSQL 하나, Percona PMM은 VictoriaMetrics + PostgreSQL 둘입니다. 장기 보관은 아예 범위 밖으로
빼고 lakehouse 몫이라 적었습니다 — 메타 DB에는 7일치만 둡니다.

## 변경 실행의 안전

**Q. 승인된 변경만 실행한다는 것을 어떻게 보장했나요? SQL을 파싱해서 검사하나요?**
파싱에 안전을 걸지 않았습니다. 실행권은 조건부 UPDATE로 한 요청만 얻고, 같은 트랜잭션에서 변경 전 사본을 락과 함께 잡은 뒤 영향 행 수가 사본 행 수와 같을 때만 커밋합니다.
파서가 틀리거나 동시 변경이 끼면 커밋되지 않습니다. 사본 조회를 일부러 틀리게 준 계획은 커밋 0이었습니다(130절).

**Q. 100만 행을 고쳐야 하면요? 사본을 100만 개 뜨나요?**
아니요. 그 방식은 안전의 대가가 행 수에 비례합니다 — 10,000행에서 락 보유가 PostgreSQL 67.1ms·MySQL 75.2ms였고, 동시 쓰기가 있으면 남의 쓰기 p95가 69~87ms까지 밀렸습니다.
100만 행이면 한 트랜잭션이 수 초~수십 초를 쥐고 복제도 한꺼번에 밉니다. 그래서 대량은 기본 키 범위 배치(기본 1,000행·쉼 100ms)로 쪼개 구간마다 따로 커밋하고,
되돌리기는 사본이 아니라 복원 검증에 성공한 최근 백업을 실행 전 조건으로 겁니다. 그 백업이 없으면 실행을 거부합니다(196·197절).

**Q. 배치로 쪼개면 정말 덜 미나요? 총 소요는 오히려 길어질 텐데요.**
100만 행에서 쟀습니다. 한 문장으로 돌리는 동안 동시 작성자 둘은 130번밖에 커밋하지 못했는데, 배치로 쪼개자 MySQL 76,970번·PostgreSQL 173,167번 커밋했습니다.
최대 대기는 22.9초에서 0.64초로 내려왔습니다. 총 소요는 배치가 6.5~13.6배 길지만 그중 100초는 일부러 자는 시간(배치 1,000개 × 쉼 100ms)이고, 빼면 2.2~3.1배입니다.
총 소요를 그대로 비교하면 안 된다는 뜻입니다(198절).

**Q. 배치가 도는 중에 취소하면 앞서 바뀐 행은 되돌아가나요?**
되돌아가지 않습니다. 대량 변경은 부분 적용이 정상 상태이고, 조용히 절반만 되돌리는 쪽이 더 위험합니다. 대신 마지막으로 적용을 마친 키를 남겨 "어디까지 적용됐나"를
한 값으로 답하고, 되돌릴지는 사람이 그 키와 백업을 보고 판단합니다. 화면도 그 문장을 그대로 적습니다.

**Q. 커밋 호출이 실패하면 어떻게 하나요?**
대상 DB가 롤백을 확정한 실패는 실행권을 돌려줘 다시 실행할 수 있게 하고, 커밋 여부를 모르면 돌려주지 않습니다. 사람이 대상 DB를 무엇으로 확인했는지 근거를 적어야만 정리됩니다.
플랫폼이 다시 봐서 자동 판정하면 "모른다"를 "안다"로 바꾸는 순간 두 번 실행될 수 있기 때문입니다(130·131절).

**Q. 복합 기본 키는 어떻게 자르나요?**
사전순 한 덩이로 비교합니다. `(shop_id, id) > (?, ?)`이지 `shop_id > ? AND id > ?`가 아닙니다. 열마다 부등호를 따로 쓰면 구간이 겹치거나 비어 행이 빠집니다.
20만 행에서 경계 `(2, 49999)` 뒤에 남은 행을 세면 사전순 비교는 100,001행, 열별 비교는 2행입니다. **99,999행이 오류 없이 빠집니다**(200절).

**Q. 그 사전순 비교를 기종마다 다르게 적는다고요? 같은 SQL이면 안 되나요?**
안 됐습니다. SQL Server는 행 값 비교 문법 자체가 없어 파싱에서 죽습니다(`Msg 4145`). MySQL은 문법은 받지만 조건을 인덱스 **범위**로 내리지 않아
배치가 뒤로 갈수록 앞 구간을 다시 훑습니다 — 경계가 깊어지면 훑는 행이 1,001에서 191,000으로, 0.27ms에서 30.5ms로 늘었습니다.
같은 뜻을 `(a > ?) OR (a = ? AND b > ?)`로 펼치면 MySQL은 범위 조회가 되지만(10,000행 2.6ms), PostgreSQL은 비트맵 스캔이 인덱스 순서를 잃어
`Sort`가 붙고 오히려 느려집니다(0.60 -> 3.19ms). 경계 조회는 `ORDER BY 키 LIMIT n`이라 순서가 곧 성능입니다.
그래서 한 형태로 통일하지 않고 기종이 고르게 했습니다. Oracle은 두 형태를 같은 계획으로 정규화해(plan hash 동일) 이 방법으로는 안 고쳐지고,
5.9배는 MySQL의 113배와 성격이 달라 **고치지 않기로 하고 수치를 남겼습니다**(200절).

**Q. 인덱스를 타는데 왜 느린가요? 인덱스를 더 걸면 되지 않나요?**
그게 인덱스 문제가 아니라는 것을 실측으로 확인했습니다. 보조 인덱스 `(shop_id, id)`를 따로 걸어도 훑는 행은 200,000행 그대로였고 읽는 인덱스만 바뀌었습니다(32.4 -> 49.2ms).
`EXPLAIN`에 `key: PRIMARY`가 보이면 인덱스를 쓰는 것 같지만 `type: index`는 **인덱스 전체 훑기**입니다. 범위로 타는 것은 `type: range`고,
같은 인덱스에서 술어를 어떻게 쓰느냐로만 갈렸습니다. 이 둘을 같게 읽으면 "인덱스를 더 걸자"는 엉뚱한 결론이 나옵니다(200절).

**Q. 최소 권한 계정이 실제 변경을 막은 사례가 있나요?**
검증용 외래키를 제품 흐름 그대로 요청자 제출, 승인자 승인, 운영자 실행으로 올렸습니다. PostgreSQL은 변경 계정이 소유자 역할 멤버라 통과했지만, MySQL과 SQL Server는
가리키는 테이블의 `REFERENCES` 권한이 없어 실행이 FAILED로 남았습니다. 계정 구성을 최소로 넓힌 뒤 같은 승인 티켓을 다시 실행해 MySQL은 affectedRows 2000,
SQL Server는 affectedRows 0으로 COMMITTED가 됐고, 최종 기록에는 requester·decidedBy·executedBy가 각각 다른 사람으로 남았습니다(151절).

**Q. 실행 기록의 구조 비교가 사실과 달랐던 적이 있나요?**
있었습니다. 외래키를 추가한 세 실행 모두 구조 비교가 `identical: true`였고, 화면은 "구조 차이가 없습니다"라고 했습니다. 당시 구조 스냅샷이 열과 인덱스만 담았기 때문입니다.
그래서 먼저 문구를 정직하게 바꾸고(151절), 다음 절에서 스냅샷과 diff 모델에 외래키를 넣었습니다. MySQL에서 외래키를 지우는 티켓 #74는 removedForeignKeys,
다시 만드는 티켓 #75는 addedForeignKeys로 잡혔고, 둘 다 `identical = false`였습니다(153절).

## AI

**Q. Pi 같은 로컬 코딩 에이전트가 `AGENTS.md` 지침을 무시하고 `git push`나 운영 DB 명령을 호출하면 어떻게 하나요?**
`AGENTS.md`는 작업 방법을 설명하는 컨텍스트이고, `.pi/extensions/dbtower-policy.ts`는 Pi의 `tool_call` 직전에 경로·도구·명령·승인 ID를 검사하는 보조 실행 경계입니다. 기본 `readonly` 정책은 읽기 도구만 열고, `change` 정책도 작업공간 안의 파일 변경과 검증 명령만 허용하며 `git push`, `kubectl`, `terraform apply`, 운영 DB 클라이언트와 셸 우회를 차단합니다. 파일 변경 뒤 테스트가 성공하지 않으면 다음 에이전트 턴을 검증 요청으로 되돌리고 모든 판정을 감사 파일에 남깁니다(168절).

Pi 확장은 전체 시스템 권한으로 실행될 수 있어 서버 보안의 대체물이 아닙니다. Pi를 거치지 않은 curl·MCP 요청이나 악성 확장은 로컬 확장으로 막을 수 없으므로, 실제 대상 DB 변경은 여전히 DBTower의 요청자→승인자→운영자 전이, 조회 계정·읽기 전용·행 사본 대조·감사 경계를 통과해야 합니다. 네트워크 접근 확장도 필수로 설치하지 않고 출처와 권한을 검토한 뒤 선택합니다.

**Q. AI에게 실행 권한을 왜 주지 않았나요?**
기업형 Text-to-SQL 벤치마크(Spider 2.0) 정확도가 20%대라, 실행 경계는 AI와 무관하게 서 있어야 한다고 봤습니다. AI는 SQL 텍스트만 내고, 그 텍스트는 사람이 실행할 때
조회 계정·읽기 전용·마스킹 경계를 다시 지납니다. 데모 스키마 12문항을 실행 결과로 채점해 lenient 12/12, strict 7/12였고, 이 수치는 프롬프트 변경의 전후 비교용이지 벤치마크 비교용이 아니라고 적었습니다(129절).

**Q. AI 답을 흘려 보여주면, 흘러간 내용과 저장되는 답이 달라질 수 있지 않나요?**
흘린 조각은 보여주기만 합니다. 워크벤치 AI는 JSON 하나로 답하는데, 흘러오는 동안에는 미완성 JSON에서 설명·SQL 값의 앞부분만 뽑아 보이고, 저장·문장 분류·버전 카드는 완성본을 다시 파싱해 만듭니다.
max_tokens에 잘린 응답은 조각이 이미 화면에 흘렀어도 완성본으로 올라가지 않습니다. 같은 질문 셋에서 첫 설명이 4.45·10.01·4.55초에, 완성본이 10.85·19.96·12.10초에 왔습니다(141절).

**Q. 나중에 찾은 AI 스트리밍 결함은 무엇이었나요?**
AI를 흘려 보여도 메서드 전체 트랜잭션 안에서 AI를 기다리면 플랫폼 DB 커넥션을 오래 쥡니다. 재감사에서 변경 요청·워크벤치 AI의 동시 스트림 4건 동안 active 커넥션 4개를 확인했고,
저장 구간만 트랜잭션으로 묶어 active 0으로 바꿨습니다. 또 CLI 경로가 stdout을 다 읽은 뒤에야 시간 초과를 재서 멈춘 자식을 못 죽이던 것을 20초 넘김에서 0.11·2.01초 종료로 고쳤습니다(148절).

**Q. 프롬프트 인젝션은 어떻게 막았나요?**
세션 쿼리 텍스트처럼 대상 DB 사용자가 쓴 문자열이 AI 입력이 되므로, 프롬프트를 경계로 믿지 않았습니다. 도구 호출 정책을 순수 함수로 떼어 대상 인스턴스 id를 고정하고,
검사한 값을 정규화해 실행한 값과 일치시켰습니다. 가드를 걷어내면 새 테스트 2건이 실패하는 뮤테이션으로 테스트가 실제로 막는지 확인했습니다(126절).

**Q. AI가 지어낸 수치를 어떻게 막나요?**
모델 소견의 수치와 인용을 플랫폼이 모은 사실·규칙 판정·참고 자료와 글자로 대조합니다. 어긋나면 거부하지 않고 "검증되지 않음" 목록으로 남겨 소견보다 먼저 보여줍니다 — 확인할 수 없는 수치를 확인된 사실처럼 보여주지 않는 쪽을 택했습니다.
이 검사가 실측에서 두 번 틀렸고 둘 다 고쳤습니다: 분석 구간 시각을 숫자 다섯 개로 쪼개 정직한 답변에 경고 6줄을 붙였고, 단위가 붙은 `350ms`를 놓쳐 지어낸 값이 통과했습니다(169절).

**Q. 왜 플랫폼에 Redis를 두지 않았나요?**
큐 장애가 플랫폼을 흔들지 않게 하려고 실행면(Python)에 두었습니다. 대가는 HTTP 왕복과 중복 발행입니다 — 발행 직후 릴레이가 죽으면 리스 만료 뒤 다시 발행되고(유실보다 중복을 택함), 그 중복은 작업 선점이 흡수합니다(두 번째 배달은 409). 플랫폼은 Redis를 모릅니다(169절).

**Q. 큐가 죽으면 작업은 어떻게 되나요?**
접수와 같은 트랜잭션에 Outbox를 남기므로 작업은 사라지지 않습니다. 릴레이가 멈추면 미발행 이벤트가 쌓이고, 실행기가 죽으면 리스가 만료돼 리퍼가 실패로 드러냅니다 — 조용히 다시 흘리지 않고 자동 재시도도 하지 않습니다. 원인을 본 사람이 `POST /retry`로 되돌립니다. 아무도 가져가지 않은 작업도 30분이 지나면 실패로 드러냅니다(169절).

**Q. 승인은 누가 하나요? AI 운영 작업에 승인 상태를 두지 않은 이유는요?**
변경 승인은 review 모듈이 단일 권위입니다. AI 운영 작업에 승인 대기 상태를 따로 두면 승인 권위가 둘이 되므로 두지 않았습니다. 모델이 조치 목록에 변경 행위를 넣으면 결과에 `approvalRequired`만 남기고, 실제 변경은 기존 변경 요청 티켓(요청자→승인자→운영자)을 거칩니다(169절).

## 검증과 측정

**Q. 읽기 전용 트랜잭션은 어떻게 검증했나요?**
쓰기 권한 계정으로 INSERT를 넣어 봤습니다. 같은 `setReadOnly(true)`가 MySQL은 드라이버와 서버에서, PostgreSQL은 서버에서 막았고, Oracle은 아무것도 막지 않아
끝의 롤백만 막고 있었습니다. Oracle에만 `SET TRANSACTION READ ONLY` 훅을 넣었습니다(128절).

**Q. 성능 수치를 어떻게 믿을 수 있나요?**
같은 부하를 변경 전후에 걸어 재고, 흔들리는 수치는 근거에서 뺐습니다. SQL Server를 GitHub Actions x64 러너에서 두 번 재니 서버 실행 시간이 53,052 -> 75.1 µs와
122,541 -> 173.0 µs로 두 배 넘게 달랐습니다. 첫 실행만 보고 적었던 "Rosetta가 1.3~1.9배 느리다"는 해석을 거두고, 세 실행 모두 같았던 실행계획과 논리 읽기(3,973 -> 63)만 남겼습니다(134절).

**Q. 단위 테스트는 통과했는데 라이브에서 드러난 결함이 있었나요?**
Oracle Data Guard 지연 쿼리의 `value != ''`는 빈 문자열을 NULL로 보는 Oracle에서 항상 거짓이라 지연을 한 번도 못 쟀습니다. H2 테스트에서는 다른 DB처럼 동작해 초록이었습니다.
실제 Data Guard를 세워 서버 41초와 플랫폼 41.0초 일치를 확인했습니다(123.15절). 최근에는 외래키 티켓이 최소 권한에 막힌 사례와, 구조 비교가 외래키를 못 보던 사례처럼
제품 흐름을 끝까지 밟아야 보이는 결함이 이어졌습니다(151·153절).

**Q. 게시한 릴리스가 깨져 있던 적이 있나요?**
있습니다. v1.6.0 변경 이력에 "대량 일괄 변경이 5기종 전부에서 돈다"고 적었는데, SQL Server에서 복합 키 배치가 문법 오류로 죽었습니다(단일 키는 정상).
복합 키 통합 테스트가 MySQL·PostgreSQL만 덮어, 기종 확장과 복합 키가 **곱해지는 자리**를 비운 채 게이트를 통과했습니다. 축을 각각 덮는 것과 조합을 덮는 것은 다른 일이었습니다.
찾은 경로가 더 남습니다 — 코드 주석이 `(200절)`을 참조하는데 문서에 그 절이 없어, 기억으로 채우지 않고 다시 재다가 드러났습니다.
같은 측정에서 주석이 틀린 것과 성능 결함 하나가 더 나왔습니다. v1.6.1로 고쳤고, **v1.6.0 절의 틀린 문장은 지우지 않고 정정 문단을 위에 붙였습니다** —
그 이미지를 받아 간 사람에게는 무엇이 틀렸는지가 여전히 사실이기 때문입니다(200절).

**Q. 그 결함을 막을 테스트를 추가했으면 끝인가요?**
아닙니다. 고치고 보니 SQL Server CI 잡의 테스트 목록에 대량 변경 통합 테스트가 아예 없었습니다. **테스트를 쓰는 것과 CI가 그것을 돌리는 것은 다른 일이었습니다.**
게다가 이 테스트들은 게이트 환경변수로 막혀 있어, 변수를 못 받으면 전부 건너뛰고도 초록불이 뜹니다 — 초록불이 "확인했다"가 아니라 "아무것도 안 했다"를 뜻할 수 있는 자리입니다.
목록에 넣고, 결과 파일을 읽어 복합 키 테스트가 건너뛰어지지 않았는지 단언하는 검사를 함께 걸었습니다. 릴리스 워크플로가 브라우저 E2E에 이미 쓰던 장치입니다.
고친 코드를 일부러 되돌려 돌려, 테스트가 원래 결함을 그대로 잡는 것도 확인했습니다.

**Q. 원시 NUL 바이트 사건은 왜 중요한가요? 동작은 정상이었다면서요?**
동작은 정상이었지만 리뷰 가능성이 깨졌습니다. 153절 커밋 통계에서 Java 소스가 `Bin 8425 -> 9147 bytes`로 찍혀 확인해 보니, 150·151절에 커밋된 Java와 JS 파일에
맵 키 구분자용 실제 NUL 한 바이트가 들어 있었습니다. git은 파일을 바이너리로 보고 PR diff를 숨기고, `grep`도 못 찾습니다. 값은 그대로 두고 소스 표기만 `\\u0000` 이스케이프로 바꿨고,
규약 검사에 "추적 파일의 원시 NUL 바이트 금지"를 추가했습니다. 탐침 파일은 실패로 잡고, 제거 뒤 추적 파일 전수 검사는 NUL 0이었습니다(154절).

## 장애 대응

**Q. 가장 기억에 남는 장애 분석은?**
검증용 등록을 지우는데 삭제 API가 2분 넘게 돌아오지 않았습니다. 스레드 덤프를 보니 연결만 받고 말이 없는 대상 하나에서 SQL Server 풀 생성이 prelogin 읽기에 매달린 채
`computeIfAbsent` 락을 쥐고 있었고, 모든 대상의 폴러와 삭제 API가 그 뒤에 줄을 섰습니다. 소켓 서버로 재현 테스트를 먼저 만들었고(25초 초과), 긴 백업을 끊지 않도록
로그인 단계에만 읽기 제한을 걸어 약 2초로 줄였습니다(134절).

**Q. 페일오버를 왜 자동으로 하지 않나요?**
관제 도구가 승격까지 하면 그 도구가 죽을 때 감지와 실행을 함께 잃고, 클러스터 매니저와 판단이 갈리면 스플릿 브레인 위험이 생깁니다. 역할 변경과 split-brain은 감지해 경보하고,
승격·펜싱은 정족수를 가진 클러스터 매니저에 맡깁니다(123.17절).
