# DBTower 한 장 요약

이기종 DBMS 5종(MySQL·PostgreSQL·SQL Server·Oracle·MongoDB)을 인터페이스 하나 뒤에 두고, 관제·진단·변경을 **쓰는 사람별 입구**로 여는 셀프호스트 운영 관리 플랫폼.
Java 21, Spring Boot 4, Spring Modulith(모듈 17개, 경계는 빌드가 검사).

자세한 근거는 [PORTFOLIO-AX](PORTFOLIO-AX.md)(사례 11개)와 [VERIFICATION](../verify/VERIFICATION.md)(명령·출력 원문)에 있다. 이 문서는 그중 DBMS 운영 관리 직무에 맞는 넷만 추린다.

## 풀려는 문제

- DB 이슈가 나면 개발자는 기종마다 흩어진 지표를 오가다 결국 DBA에게 묻는다. DBA는 같은 질문에 반복해서 답한다.
- 변경은 DB 클라이언트에서 따로 실행돼, 승인된 SQL과 실행된 SQL이 같다는 증거도, 되돌릴 사본도, 전후 비교도 남지 않는다.
- 관리 대상 DB가 늘수록 사람 손이 선형으로 는다.

## 만든 것

| 영역 | 내용 |
|---|---|
| 관제 | 쿼리 통계 load%, 시점 비교(평소 구간 대 문제 구간), 회귀·이상 자동 감지와 웹훅, 통합 헬스 스코어, 복제 지연 5기종 실측, 실시간 세션·블로킹(서버 허브 SSE, 앱 노드 여럿이어도 대상 조회 한 번) |
| 진단 | 실행계획 규칙 지적, AI 1차 분석(판단 기준 문서 위에서만, 계획은 AI를 기다리지 않고 먼저), 실제 실행 계획으로 추정 대 실제 괴리를 짚는 심층 진단, 인덱스 어드바이저(HypoPG 가상 인덱스) |

| 변경 | 거버넌스 SQL 워크벤치. 조회는 분리된 조회 계정·읽기 전용 트랜잭션·마스킹·감사, 변경은 승인된 티켓만 사본·되돌리기와 함께 실행 |

| 사람 | 관제·요청자·승인자·운영자·관리자 5역할. 승인자와 운영자는 서로의 일을 하지 못한다 |
| 화면 | 관제와 워크벤치를 한 페이지의 두 모드로(새 탭 없는 넘김), 스키마 트리(테이블/뷰·기본키·인덱스)와 테이블 상세(외래키를 가리키는 쪽·가리켜지는 쪽 모두)를 5기종 같은 모델로. 관제 AI 채팅은 대화를 서버에 저장하고(대화 목록·이어 묻기), AI로 보내는 쿼리와 실행계획의 값은 가림 수준 셋 중에 골라 가린다 — 값을 지우되 모양(`%` 위치·자릿수·날짜 거리)을 남기는 중간 단계를 둔 이유는, 값이 아니라 구조가 진단의 근거이기 때문이다(176·177·195절) |

## 대표 사례 넷

### 1. 승인된 변경만 실행한다: 안전을 SQL 파싱이 아니라 트랜잭션 불변식에 건다

실행권은 `status = 'APPROVED'` 조건부 UPDATE로 한 요청만 얻는다. 같은 트랜잭션에서 변경 전 행 사본을 락과 함께 잡고, 대상 DB가 보고한 영향 행 수가 사본 행 수와 같을 때만 커밋한다.
되돌리기는 실행 직후 사본과 지금 행이 같을 때만 파라미터 바인딩으로 쓴다.

- 실DB(MySQL 8.4·PostgreSQL 16·Oracle 23ai)에서 UPDATE·DELETE·INSERT를 되돌린 뒤 원래 행과 문자열 일치, 사본 조회를 일부러 틀리게 준 계획은 커밋 0
- 동시 실행 2건 `[200, 409]`, 이후 SQL Server·MongoDB까지 5기종 확장 ([사례 5·6](PORTFOLIO-AX.md), VERIFICATION 130·131절)

**같은 원칙을 대량에 옮길 때는 근거를 바꿔야 했다.** 사본 방식은 10,000행에서 락 보유가 67~75ms이고 행 수에 비례해 는다. 그래서 수십만 행은
기본 키 범위 배치로 쪼개 구간마다 커밋하고, 되돌리기를 사본이 아니라 **복원 검증된 최근 백업**에 건다(없으면 실행 거부). 이 경로의 불변식은
"영향 행 수가 목표 배치 크기를 넘으면 커밋하지 않는다"이다. 100만 행 실측에서 한 문장 실행은 동시 작성자를 사실상 멈춰 세웠고(23.2초 동안 커밋 130번),
배치는 같은 작성자가 76,970번 커밋하게 했다. 최대 대기 22.9초 -> 0.64초 (VERIFICATION 196~198절)

**구간을 어떻게 자르느냐가 기종마다 다르다.** 복합 키는 사전순 한 덩이로 비교해야 한다 — 경계 `(2, 49999)`에서 남은 행이
사전순 비교는 100,001행, 열마다 부등호를 따로 쓰면 2행이다. **99,999행이 오류 없이 빠진다.** 그런데 그 사전순 비교를
SQL Server는 문법으로 아예 받지 않고(`Msg 4145`), MySQL은 받지만 인덱스 범위로 내리지 않아 배치가 뒤로 갈수록 앞 구간을 다시 훑는다
(경계가 깊어지면 훑는 행 1,001 -> 191,000, 0.27 -> 30.5ms). 같은 뜻을 펼쳐 쓰면 MySQL은 범위 조회가 되지만(10,000행 2.6ms)
PostgreSQL은 비트맵 스캔이 인덱스 순서를 잃어 오히려 느려진다(0.60 -> 3.19ms). 그래서 한 형태로 통일하지 않고 기종이 고르게 했다 (200절)

### 2. 권한 경계는 프롬프트가 아니라 코드가 지킨다

자연어 진단 루프는 서비스 토큰으로 돌아 팀 범위가 꺼져 있었고, 대상 인스턴스를 묶는 장치는 시스템 프롬프트 한 줄이었다. 도구 호출 정책을 순수 함수로 떼어 대상 id를 고정하고,
뮤테이션(가드를 걷어내면 새 테스트 2건 실패)으로 테스트가 실제로 막는지 확인했다. 뒤이어 MCP 채널이 요청자 신원을 서비스 토큰으로 바꿔 승인 분리를 비껴가던 결함을 수정 전 코드로 재현해 닫았다.

- 자기 승인 HTTP 200 -> 409, 기록된 요청자 `api-token` -> 실제 사용자 ([사례 1·7](PORTFOLIO-AX.md), VERIFICATION 126·132절)

### 3. 대상 하나의 장애가 플랫폼 전체를 멈추지 않게

측정을 마치고 검증용 등록을 지우는데 삭제 API가 돌아오지 않았다. 스레드 덤프를 보니 연결만 받고 말이 없는 대상 하나에서 SQL Server 풀 생성이 prelogin 읽기에 매달린 채
`ConcurrentHashMap.computeIfAbsent` 락을 쥐고 있었고, 모든 대상의 운영 경보·헬스 스코어 폴러가 그 뒤에 줄을 섰다. 소켓 서버로 재현 테스트를 먼저 만들고,
긴 서버 사이드 백업은 끊지 않도록 로그인 단계에만 읽기 제한을 걸었다.

- 재현 테스트: SQL Server·Oracle 헬스체크 25초 초과 -> 약 2초, 로그인 뒤 7초 서버 대기는 끝까지 받음 ([사례 9](PORTFOLIO-AX.md), VERIFICATION 134절)

### 4. 한 플랫폼, 사람별 입구

관제와 워크벤치를 두 제품으로 나눌지 검토했다. 둘은 인스턴스·팀 범위·감사·티켓을 공유하고 운영자의 한 흐름이 두 화면을 오가므로 제품은 하나로 두고, 역할을 쓰는 사람 기준으로 나눴다.
인가 경계 24개가 전부 ADMIN이던 것을 운영자 12·관리자 9·승인자 2 등으로 재배치하고, 화면은 역할 이름이 아니라 능력(capabilities)으로 버튼을 가른다.

- 실DB 한 티켓에서 요청·승인·실행·되돌리기가 서로 다른 세 사람으로 기록, 승인자의 실행 시도 403 ([사례 10](PORTFOLIO-AX.md), VERIFICATION 135절)
- 다섯 역할 화면을 실제 브라우저로 눌러 결함 둘(안내 레이아웃, UTC 시각 표시)을 찾아 고치고, 같은 확인을 CI의 브라우저 테스트로 고정 (VERIFICATION 136·137절)

## 테스트가 초록이어도 라이브가 잡은 결함

- Oracle Data Guard 복제 지연 쿼리의 `value != ''`는 빈 문자열이 NULL인 Oracle에서 항상 거짓이라 지연을 한 번도 못 쟀다. 실제 Data Guard 앞에서 서버 41초와 플랫폼 41.0초 일치를 확인했다(123.15절).
- PostgreSQL은 복제본 없는 primary를 STANDALONE으로 보고해, primary 개수로 세던 split-brain 감지를 놓쳤다(123.17절).
- 읽기 전용 트랜잭션을 쓰기 권한 계정으로 검증하니 `setReadOnly(true)`가 Oracle에서 아무것도 막지 않았다(128절).
- 실시간 허브를 두 노드로 조율하니 대상 조회는 절반이 됐지만 사람당 프레임이 15장이 아니라 12·11장이었다. 두 노드의 틱이 겹치면 조회권을 못 잡은 노드가 올라오기 전에 읽었다.
  0.5초 뒤 한 번 더 읽게 고쳐 두 노드 모두 15장, 같은 번호를 받았다(144절).
- 멈춘 AI CLI 자식을 시간 초과로 끊는 테스트가 macOS에서는 2초대에 끝났지만 Linux CI에서 20초를 넘겼다. 셸이 남긴 자손 프로세스가 출력 파이프를 쥐고 있었다.
  자손까지 먼저 죽이게 고쳐 2.01초에 끊긴다(148절).
- 검증용 외래키를 제품의 승인 티켓으로 올리니 MySQL·SQL Server에서 승인까지 통과한 뒤 실행이 거부됐다. 변경 계정에 가리키는 테이블의 REFERENCES 권한이 없었다.
  같은 실행 기록의 구조 비교는 외래키를 보지 못해 "차이 없음"이라 적었다(151절).
- **낸 릴리스가 깨져 있었다.** v1.6.0 변경 이력에 "5기종 전부에서 돈다"고 적었는데 SQL Server에서 복합 키 배치가 문법 오류로 죽었다.
  복합 키 테스트가 MySQL·PostgreSQL만 덮어, 기종 확장과 복합 키가 **곱해지는 자리**를 비운 채 게이트를 통과했다.
  찾은 경로가 더 중요하다 — 코드가 `(200절)`로 참조하는데 문서에 그 절이 없어, 기억으로 적지 않고 다시 재다가 드러났다.
  같은 측정에서 주석이 틀린 것(MySQL이 커버링 스캔이라고만 적고 범위 스캔이 아니라는 것을 빠뜨림)과 성능 결함 하나가 더 나왔다(200절).
- **저장 구조를 점검하다 "삭제 코드 없는 표 셋"을 한 묶음으로 본 것이 틀렸다.** 원인이 전부 달랐다 —
  `login_attempt`은 사용자명이 기본 키라 애초에 행이 늘지 않고, 감사 기록 둘은 영구 보존이 맞았다.
  **없는 것을 세는 것만으로는 판단이 안 된다.** 고친 것은 코드가 아니라 기록이었다(201절).
- **조용히 안 지워지는 함정을 두 번 밟았다.** `ash_sample`을 일별 파티션으로 옮기면서, 정리 잡의
  정규식이 일 파티션 이름을 못 읽는 것과 부모를 `RENAME`해도 자식 이름이 그대로 남는 것을 연달아 만났다.
  둘 다 오류가 나지 않아 배포 뒤에는 보이지 않는다 — 실제 PostgreSQL에 마이그레이션 49개를 돌려서야
  드러났고, H2 테스트는 셋 다 통과했다(201절).
- **테스트를 쓰는 것과 CI가 그것을 돌리는 것은 다른 일이었다.** 위 결함을 고치고 보니 SQL Server CI 잡의 테스트 목록에
  대량 변경 통합 테스트가 아예 없었다. 게이트 환경변수를 못 받으면 전부 건너뛰고도 초록불이 뜬다 — **초록불이 "확인했다"가 아니라
  "아무것도 안 했다"를 뜻할 수 있는 자리다.** 목록에 넣고, 결과 파일을 읽어 실제로 돌았는지 단언하는 검사를 함께 걸었다(#140).

## 대역이 통과시킨 것은 통과한 게 아니다

위 결함 중 셋이 같은 모양이다. 전부 **검증 환경이 실물과 다른 자리**에서 났다.

| 무엇이 대역이었나 | 무엇을 못 봤나 |
|---|---|
| 합성 픽스처(SQL Server 계획) | 실제 계획의 `StatementText` 에 사용자가 친 SQL 이 통째로 들어 있었다(195절) |
| 복합 키 테스트가 MySQL·PostgreSQL 만 | SQL Server 에 행 값 비교 문법이 없어 게시된 릴리스가 깨져 있었다(200절) |
| H2 가 만든 테스트 스키마 | 마이그레이션의 컬럼 정의가 틀려도 통과했다. JPA 엔티티가 H2 스키마를 대신 만들기 때문이다(201절) |

셋 다 **테스트는 초록이었다.** 실제 SQL Server 계획을 캡처해서, 5기종 전부에 통합 테스트를 돌려서,
실제 PostgreSQL 에 마이그레이션 49개를 적용해서 각각 드러났다.

대역을 쓰지 않는다는 뜻이 아니다. H2 없이는 테스트가 도커 없이 안 돌고, 합성 픽스처 없이는 계획 파서를
못 만든다. **대역이 덮지 못하는 축이 무엇인지 알고, 그 축만 실물로 한 번 밟는다**는 뜻이다.

## 아직 못 한 것

- AI 운영 작업의 실 Slack 워크스페이스는 없다. 서명·중복·스레드 응답은 로컬 서명 요청과 기록 서버까지 검증했다.
- Vertex AI 백엔드는 자격증명이 없어 구현하지 않았다. 모델 호출이 `AiAnalyzer` 한 곳을 거쳐 늘릴 자리는 분명하다.
- 참고 자료 검색 품질은 상위 3개 중 관련 절 11/27이 남은 한계다(169절).
- **AI로 나가는 값의 가림은 기본값이 여전히 꺼짐이다.** 켜는 쪽으로 바꾸겠다고 이슈에 적어 두고 근거를 보강했는데,
  판정자 셋의 일치가 착수 전에 정한 기준(80%)에 못 미쳐(51%) 바꾸지 않았다. 기준표를 고쳐 일치를 올리려던 시도는
  오히려 34%로 떨어뜨렸다 — 기준표에 나열한 불확실 표현이 응답 162건 **전부**에 들어 있어, 규칙이 검사 가능해 보였을 뿐이었다.
  대신 원인은 찾았다. 판정자를 동질하게 맞추고 실행 조건을 고정하니 같은 기준표에서 51% -> 70%로 올랐다.
  **낮은 일치는 기준표가 아니라 섞인 판정자 묶음 탓이었다.** 세 판정자 모두 순서는 같아(`NONE` > `STRUCTURE` > `FULL`),
  켰을 때의 수준을 `STRUCTURE`로 두는 근거는 선다(`experiments/ai-masking-levels.md`).
- 경보에서 작업이 자동으로 생기는 경로는 라이브로 밟았다(170절: 회귀 -> 경보 -> 작업 -> 팀 채널 47.4~60.9초). 기본값은 여전히 꺼짐이고,
  채널 표에 없는 팀은 Slack으로 보내지 않아 결과를 화면에서만 볼 수 있다.
