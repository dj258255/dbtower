# DBTower AX 케이스 스터디: AI를 DB 운영 플랫폼에 안전하게 들이기

플랫폼 엔지니어링 관점에서 "AI 기능을 붙인다"를 "AI가 지켜야 할 정책을 플랫폼이 보장한다"로 바꿔 푼 기록이다.
기능 소개는 [README](../README.md)와 [PRESENTATION](PRESENTATION.md)에, 명령·출력 원문은
[VERIFICATION](VERIFICATION.md)에 있다. 이 문서는 그 사이에서 **문제, 결정, 트레이드오프, 실측**만 사례 단위로 모은다.

## 한 줄 요약

자연어로 DB를 보고 고치는 사내 플랫폼을 만들되, 권한·마스킹·감사·실행 승인은 프롬프트가 아니라 플랫폼 코드가
강제한다. AI는 판단자가 아니라 1차 분석기로 둔다.

## 왜 이 방향인가

DB팀의 반복 문의("이 쿼리 왜 느려요", "이 테이블 좀 봐주세요")를 셀프서브로 돌리는 것이 출발점이다.
여기에 자연어 AI를 붙이면 편해지지만, 동시에 세 가지 위험이 생긴다.

| 위험 | 실제 사례 | DBTower의 대응 원칙 |
|---|---|---|
| 데이터에 심긴 지시문이 AI를 조종한다(프롬프트 인젝션) | Supabase MCP 유출 시연(2025-07): 지원 티켓 본문의 지시문으로 DB 내용 유출 | 도구 호출의 대상·범위를 코드로 고정한다 |
| 읽기 전용 보호가 문자열 검사라 뚫린다 | 참조 Postgres MCP 서버: `COMMIT; DROP ...`으로 읽기 전용 트랜잭션 탈출 | 실행 계층(계정 권한·읽기 전용 트랜잭션·타임아웃)으로 겹친다 |
| 업무 데이터가 외부 LLM으로 나간다 | 사내 Text-to-SQL 전반의 공통 과제 | AI에는 기본으로 컬럼명·행 수만, 인스턴스별로만 허용 |

설계 기준으로 삼은 레퍼런스:

- **Toss TOI**(2026-09): 개인정보 마스킹·조회 사유·다운로드 암호화는 API 프록시가 강제하고, 화면은 AI가 만든다. "정책과 화면의 분리".
- **배민 물어보새, 당근페이 브로쿼리, Uber QueryGPT**: 정확도는 모델보다 컨텍스트(메타데이터·용어·예제)에서 나오고, 사람이 확인하는 단계가 환각을 줄인다.
- **Bytebase, Alibaba DMS, Archery, 국내 DB 접근제어(Chakra Max 등)**: 사내 DB 조회의 필수 조건은 사유·마스킹·감사, 변경은 결재 후 실행과 롤백.
- **Spider 2.0**: 기업형 Text-to-SQL 에이전트 정확도가 약 21%. 자유 생성 SQL을 자동 실행하지 않고 사람이 실행 버튼을 누르게 한 근거.

## 로드맵과 결정 (2026-09-10)

| 단계 | 내용 | 상태 |
|---|---|---|
| 0 | 기존 AI 진단 루프의 권한 경계 수정 | 완료 (사례 1) |
| 0.5 | 모니터 계정 최소 권한 재실측 | 완료 (사례 2) |
| 1 | 거버넌스 SQL 워크벤치: 스키마 트리, 에디터, 결과 그리드, 마스킹, 감사, 계정 분리 | 완료 (사례 3) |
| 2 | TOI식 워크시트 + AI 제안: 워크시트별 대화, 체크포인트(버전) 카드, 선택 모드 칩, 실패 오버레이, 정확도 평가 | 완료 (사례 4) |
| 3 | 변경 티켓 실행과 전후 비교: 데이터 diff·롤백, 스키마, 실행계획·성능, 인스턴스 간 결과 | 예정 |

사람이 내린 네 가지 결정과 이유:

1. **변경은 승인 티켓만 실행한다.** 원칙을 "임의 변경 금지"에서 "승인된 변경만 플랫폼이 실행"으로 좁혀 바꾼다. 기존 리뷰 게이트(판정·AI 소견·승인·감사)를 실행까지 잇는다.
2. **AI는 조회 결과 값을 기본으로 보지 않는다.** 인스턴스별 스위치로만 마스킹된 값을 허용한다.
3. **전후 비교 4종을 전부 넣는다.** DBeaver 같은 클라이언트는 이력이 없어 "변경 전후 성능"을 못 보여준다. 스냅샷 이력이 있는 운영 플랫폼만 할 수 있는 차별점이다.
4. **SQL 에디터는 직접 구현한다.** 의존성 0 정적 SPA 규약을 지킨다.

기각한 대안: CloudBeaver·Chat2DB 임베드. 빠르지만 그 도구가 DB에 직접 붙어 마스킹·조회 사유·팀 범위·감사를 우회한다. 이 플랫폼의 가치가 바로 그 정책 계층이다.

## 사례 1. AI 에이전트의 권한 경계는 프롬프트가 아니라 코드다

근거: [VERIFICATION 126절](VERIFICATION.md)

**상황.** 자연어 진단은 AI가 읽기 도구(health, sessions, explain 등)를 스스로 골라 연쇄 호출하는 루프다.
도구 실행은 서비스 토큰(ADMIN)으로 플랫폼 자신의 REST를 다시 부른다.

**문제.** 팀 권한은 입구에서 대상 인스턴스 하나만 확인했다. 루프 안에서는 ADMIN이라 팀 범위가 꺼졌고,
도구의 대상 인스턴스를 묶는 장치는 시스템 프롬프트 한 줄이었다. 세션 쿼리 텍스트처럼 **대상 DB 사용자가 쓴 문자열**이
그대로 AI 입력이 되므로, 쿼리 주석 하나로 다른 팀 인스턴스를 조회하게 만들 수 있었다. 인스턴스 목록 도구는 전 인스턴스를
돌려줬고, 질문과 도구 호출은 감사 기록에 남지 않았다.

**결정.**
- 도구 호출 정책을 오케스트레이션에서 떼어 순수 함수(`DiagnosisGuard`)로 뺐다. 경계값을 단위 테스트로 촘촘히 검증하기 위해서다.
- 인스턴스 인자를 받는 모든 도구는 대상 id로 고정한다. 새 도구도 기본이 안전한 쪽이다.
- 핸들러가 `"2"`나 `true`를 숫자로 관대하게 변환하므로, 검사 뒤 정규화한 값으로 인자를 다시 써서 **검사한 값과 실행한 값을 일치**시켰다.
- 범위는 진단 시작 시점의 호출자 인증으로 한 번 확정하고, 질문·실행·거부를 실제 사용자로 감사에 남긴다.

**검증.**
- 공격 재현 통합 테스트: 세션 결과에 지시문을 심고 "넘어간 모델"을 흉내 내 다른 인스턴스를 요청 → REST 도달 0건.
- 뮤테이션: 가드를 걷어내면 새 테스트 2건 실패, 복원하면 통과. 전체 576 테스트 통과.
- 라이브: 팀 사용자의 진단에서 인스턴스 목록이 자기 팀 1개로 걸러지고 응답 어디에도 다른 팀 이름이 없음. 감사에 질문 1건·도구 5건이 실제 사용자로 기록.

**한계를 숨기지 않는다.** 라이브에서는 모델이 프롬프트 규약대로 스스로 거절해 거부 경로를 타지 않았다. 거부 경로는 테스트로만
증명됐다. 모델이 규약을 따르는 동안엔 프롬프트도 방어막이지만, 경계로 믿으면 안 된다는 것이 이 사례의 요지다.

**면접에서 말할 한 문장.** "AI가 규칙을 지켰기 때문에 안전했던 것과, 지키지 않아도 안전한 것은 다르다. 후자를 코드와 뮤테이션 테스트로 만들었다."

## 사례 2. 최소 권한 문서는 기능이 늘면 썩는다: "200 OK"는 통과가 아니었다

근거: [VERIFICATION 127절](VERIFICATION.md), [least-privilege.md](least-privilege.md)

**상황.** 5기종 모니터 계정의 최소 권한은 2026-07-04에 실측으로 확정해 문서와 init 스크립트에 박제했다.
그 뒤 대기 이벤트, 세션 블로킹, advisor, finops 기능이 추가됐다. 워크벤치가 조회·변경 계정을 따로 두려면
"모니터 계정이 무엇을 할 수 있는가"의 기준선이 먼저 맞아야 한다.

**문제.** 사례 1 라이브 검증 중 MySQL wait-events·sessions가 502였다. API 25개를 전부 부르니 502는 두 건뿐인데,
오퍼레이터가 읽는 테이블을 모니터 계정으로 직접 찔러 보니 누락은 **7개**였다. 두 개는 HTTP 200 응답 본문 안의
점검 항목만 `ERROR`였고, 나머지는 이 토폴로지에서 코드 경로를 타지 않았다.

**결정.**
- 기능 호출 결과가 아니라 원천 테이블 직접 조회로 누락을 확정한다.
- 부여 뒤 하나씩 회수해 최소성을 증명한다. `sys` 뷰는 INVOKER 뷰라 뷰 SELECT, 원천 테이블 SELECT, 뷰가 부르는 함수 EXECUTE가 모두 있어야 했다(단계별 에러 원문 기록).
- 관측으로 증명한 것과 코드 경로로만 확인한 것을 문서 표에서 구분한다.
- 재발 방지를 사람의 기억에 맡기지 않는다. "오퍼레이터가 읽는 테이블은 init 스크립트에 GRANT가 있어야 한다"를 빌드 규약 검사로 넣었다.

**검증 수치.** 5기종 × API 25개. MySQL 누락 7 → 0(부여 후 WARN 로그 0건), PostgreSQL·Oracle·MongoDB 누락 0.
SQL Server는 로컬 Colima(Rosetta 미사용)에서 amd64 이미지가 기동 즉시 죽어 측정하지 못했고, 사용자 VM 재시작이
필요한 조작이라 하지 않은 채 블로커로 기록했다.

**면접에서 말할 한 문장.** "상태 코드 200을 통과로 세면 권한 누락 7개 중 2개만 보인다. 원천 테이블을 직접 찔러 확정하고, 회수해서 최소성을 증명하고, 빌드가 재발을 막게 했다."

## 사례 3. "읽기 전용"을 쓰기 권한 계정으로 검증했다: 같은 JDBC 호출, 드라이버 셋, 동작 셋

근거: [VERIFICATION 128절](VERIFICATION.md)

**상황.** 사람이 자유 SQL로 대상 DB를 조회하는 거버넌스 워크벤치를 만들었다. Spider 2.0 기준 기업형 Text-to-SQL
정확도가 20%대라, 다음 단계에서 AI가 SQL을 제안하더라도 실행 경계는 AI와 무관하게 서 있어야 한다.

**결정.** 경계를 문자열 검사 하나에 걸지 않고 겹으로 쌓았다. 분류기(허용 목록) → 콘솔 계정 분리 → 읽기 전용 트랜잭션
(끝은 항상 롤백) → 결과 마스킹 → 컬럼 GRANT. 그리고 "겹이 있다"를 믿지 않고 **앞 겹을 전부 뺀 상태에서 다음 겹만으로
막히는지**를 겹마다 따로 쟀다.

**실측이 뒤집은 가정.**
- `Connection.setReadOnly(true)` 하나로 기종 분기 없이 된다고 봤다. 쓰기 권한 계정으로 INSERT를 넣어 보니 MySQL은 드라이버의
  텍스트 검사와 서버 플래그를 둘 다 걸었고, PostgreSQL은 서버가 `read-only transaction`으로 거부했고, **Oracle은 아무것도 하지
  않아 INSERT가 들어갔다**(끝의 롤백만 막고 있었다). Oracle에만 `SET TRANSACTION READ ONLY` 훅을 넣었다.
- 드라이버가 준 원래 컬럼명으로 마스킹하면 별칭을 막는다고 봤다. 라이브에서 **PostgreSQL `SELECT email AS e`가 원문 그대로**
  나왔다(pgjdbc는 원래 이름 자리에 별칭을 준다). 문장에서 별칭 쌍을 뽑아 원래 컬럼 규칙에 대도록 고쳤다.
- 이름 기반 마스킹은 `email || ''`을 원리상 못 막는다. 이걸 숨기지 않고 테스트로 "가려지지 않음"을 고정한 뒤, 본 방어선인
  **컬럼 GRANT가 같은 표현식을 `permission denied`로 막는 것**을 실측해 문서에 역할을 나눠 적었다.

**화면에서 잡은 것.** Playwright로 화면을 직접 눌러 보다가, `hidden` 속성의 모달이 CSS `display: flex`에 져서 로드 직후부터
실행 버튼을 가로막는 버그와, 로그인한 VIEWER가 ADMIN 경로를 부르면 403 대신 로그인 페이지로 튕기는 기존 버그(`/error` 재디스패치)를 잡았다.

**면접에서 말할 한 문장.** "읽기 전용이라고 쓰기 전에, 쓰기 권한 계정으로 INSERT를 넣어 봤다. 같은 표준 호출이 드라이버 셋에서 세 가지로 동작했고, 그중 하나는 아무것도 막지 않았다."

## 사례 4. AI에게 실행 권한을 주지 않고도 쓸 만하게: 제안 · 체크포인트 · 실행 결과로 잰 정확도

근거: [VERIFICATION 129절](VERIFICATION.md), [평가 러너](../scripts/eval-workbench-nl2sql.py)

**상황.** 사내 어드민 생성 플랫폼(TOI Studio) 화면을 보면 AI 대화가 "요청 → 계획 → 작업 → 체크포인트 카드"로 흐르고,
입력창의 선택 커서로 화면 요소를 찍어 요청에 붙인다. 이 경험을 DB 조회에 옮기되, AI가 대상 DB에 무엇도 실행하지 않게 하고 싶었다.

**결정.**
- AI는 **실행 도구가 없는 격리된 LLM**이다. SQL 텍스트만 내고, 그 텍스트는 사람이 실행할 때 1단계 경계(분류·조회 계정·읽기 전용·마스킹)를 다시 지난다.
  스키마·오류·대화에 지시문이 심겨도 AI가 할 수 있는 최악은 "사람이 읽을 이상한 SQL"이다.
- 제안마다 서버가 분류(읽기/승인 필요/차단)와 **스키마에 없는 테이블**을 표시한다. Uber QueryGPT가 사람 확인 단계로 풀던 환각 문제를 결정론적 대조로 먼저 걸렀다.
- 워크시트마다 대화와 SQL 버전을 **서버에** 쌓는다. 되돌리기도 새 버전이라 실행 기록과 이력이 어긋나지 않는다. 카드에는 만든 사람이 붙는다.
- 결과 값을 외부 LLM에 보낼지는 인스턴스별 ADMIN 설정이고, 꺼져 있으면 **AI 호출 전에** 거부한다.

**검증 수치.** 데모 스키마 12문항을 실행 결과로 채점해 lenient 12/12, strict 7/12(떨어진 5건은 전부 열을 더 붙인 경우),
안전 문항 2/2, 응답 중앙값 9.0초. 한계도 같이 적었다: 테이블 2개·1회 실행이라 기업 벤치마크와 비교할 수치가 아니며,
이 평가의 용도는 프롬프트·컨텍스트 변경의 전후 비교다.

**화면에서 확인한 흐름.** 질문 → 체크포인트 v1 → 미리보기 실행 → 선택 모드로 결과 열을 칩으로 → 후속 질문에 AI가 편집기 SQL과 칩을 이어받아 v2 제안 → 새로고침해도 복원.

**면접에서 말할 한 문장.** "AI에게 실행 권한을 주지 않았다. 대신 제안마다 분류와 환각 표시를 붙이고, 정확도는 AI가 낸 SQL을 실제로 실행한 결과로 쟀다."
