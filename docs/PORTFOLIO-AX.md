# DBTower AX 케이스 스터디: AI를 DB 운영 플랫폼에 안전하게 들이기

플랫폼 엔지니어링 관점에서 "AI 기능을 붙인다"를 "AI가 지켜야 할 정책을 플랫폼이 보장한다"로 바꿔 푼 기록이다.
기능 소개는 [README](../README.md)와 [PRESENTATION](PRESENTATION.md)에, 명령·출력 원문은
[VERIFICATION](VERIFICATION.md)에 있다. 이 문서는 그 사이에서 **문제, 결정, 트레이드오프, 실측**만 사례 단위로 모은다.

## 한 줄 요약

자연어로 DB를 보고 고치는 사내 플랫폼을 만들되, 권한·마스킹·감사·실행 승인은 프롬프트가 아니라 플랫폼 코드가
강제한다. AI는 판단자가 아니라 1차 분석기로 둔다.

## 왜 이 방향인가

DB팀의 반복 문의("이 쿼리 왜 느려요", "이 테이블 좀 봐주세요")를 셀프서브로 돌리는 것이 출발점이다.
여기에 자연어 AI를 붙이면 편해지지만, 동시에 세 가지 위험이 생긴다.

| 위험 | 실제 사례 | DBTower의 대응 원칙 |
|---|---|---|
| 데이터에 심긴 지시문이 AI를 조종한다(프롬프트 인젝션) | Supabase MCP 유출 시연(2025-07): 지원 티켓 본문의 지시문으로 DB 내용 유출 | 도구 호출의 대상·범위를 코드로 고정한다 |
| 읽기 전용 보호가 문자열 검사라 뚫린다 | 참조 Postgres MCP 서버: `COMMIT; DROP ...`으로 읽기 전용 트랜잭션 탈출 | 실행 계층(계정 권한·읽기 전용 트랜잭션·타임아웃)으로 겹친다 |
| 업무 데이터가 외부 LLM으로 나간다 | 사내 Text-to-SQL 전반의 공통 과제 | AI에는 기본으로 컬럼명·행 수만, 인스턴스별로만 허용 |

설계 기준으로 삼은 레퍼런스:

- **Toss TOI**(2026-09): 개인정보 마스킹·조회 사유·다운로드 암호화는 API 프록시가 강제하고, 화면은 AI가 만든다. "정책과 화면의 분리".
- **배민 물어보새, 당근페이 브로쿼리, Uber QueryGPT**: 정확도는 모델보다 컨텍스트(메타데이터·용어·예제)에서 나오고, 사람이 확인하는 단계가 환각을 줄인다.
- **Bytebase, Alibaba DMS, Archery, 국내 DB 접근제어(Chakra Max 등)**: 사내 DB 조회의 필수 조건은 사유·마스킹·감사, 변경은 결재 후 실행과 롤백.
- **Spider 2.0**: 기업형 Text-to-SQL 에이전트 정확도가 약 21%. 자유 생성 SQL을 자동 실행하지 않고 사람이 실행 버튼을 누르게 한 근거.

사람이 내린 네 가지 결정과 이유:

1. **변경은 승인 티켓만 실행한다.** 원칙을 "임의 변경 금지"에서 "승인된 변경만 플랫폼이 실행"으로 좁혀 바꾼다. 기존 리뷰 게이트(판정·AI 소견·승인·감사)를 실행까지 잇는다.
2. **AI는 조회 결과 값을 기본으로 보지 않는다.** 인스턴스별 스위치로만 마스킹된 값을 허용한다.
3. **전후 비교 4종을 전부 넣는다.** DBeaver 같은 클라이언트는 이력이 없어 "변경 전후 성능"을 못 보여준다. 스냅샷 이력이 있는 운영 플랫폼만 할 수 있는 차별점이다.
4. **SQL 에디터는 직접 구현한다.** 의존성 0 정적 SPA 규약을 지킨다.

기각한 대안: CloudBeaver·Chat2DB 임베드. 빠르지만 그 도구가 DB에 직접 붙어 마스킹·조회 사유·팀 범위·감사를 우회한다. 이 플랫폼의 가치가 바로 그 정책 계층이다.

## 사례 1. AI 에이전트의 권한 경계는 프롬프트가 아니라 코드다

근거: [VERIFICATION 126절](VERIFICATION.md)

**상황.** 자연어 진단은 AI가 읽기 도구(health, sessions, explain 등)를 스스로 골라 연쇄 호출하는 루프다.
도구 실행은 서비스 토큰(ADMIN)으로 플랫폼 자신의 REST를 다시 부른다.

**문제.** 팀 권한은 입구에서 대상 인스턴스 하나만 확인했다. 루프 안에서는 ADMIN이라 팀 범위가 꺼졌고,
도구의 대상 인스턴스를 묶는 장치는 시스템 프롬프트 한 줄이었다. 세션 쿼리 텍스트처럼 **대상 DB 사용자가 쓴 문자열**이
그대로 AI 입력이 되므로, 쿼리 주석 하나로 다른 팀 인스턴스를 조회하게 만들 수 있었다. 인스턴스 목록 도구는 전 인스턴스를
돌려줬고, 질문과 도구 호출은 감사 기록에 남지 않았다.

**결정.**
- 도구 호출 정책을 오케스트레이션에서 떼어 순수 함수(`DiagnosisGuard`)로 뺐다. 경계값을 단위 테스트로 촘촘히 검증하기 위해서다.
- 인스턴스 인자를 받는 모든 도구는 대상 id로 고정한다. 새 도구도 기본이 안전한 쪽이다.
- 핸들러가 `"2"`나 `true`를 숫자로 관대하게 변환하므로, 검사 뒤 정규화한 값으로 인자를 다시 써서 **검사한 값과 실행한 값을 일치**시켰다.
- 범위는 진단 시작 시점의 호출자 인증으로 한 번 확정하고, 질문·실행·거부를 실제 사용자로 감사에 남긴다.

**검증.**
- 공격 재현 통합 테스트: 세션 결과에 지시문을 심고 "넘어간 모델"을 흉내 내 다른 인스턴스를 요청 → REST 도달 0건.
- 뮤테이션: 가드를 걷어내면 새 테스트 2건 실패, 복원하면 통과. 전체 576 테스트 통과.
- 라이브: 팀 사용자의 진단에서 인스턴스 목록이 자기 팀 1개로 걸러지고 응답 어디에도 다른 팀 이름이 없음. 감사에 질문 1건·도구 5건이 실제 사용자로 기록.

**한계를 숨기지 않는다.** 라이브에서는 모델이 프롬프트 규약대로 스스로 거절해 거부 경로를 타지 않았다. 거부 경로는 테스트로만
증명됐다. 모델이 규약을 따르는 동안엔 프롬프트도 방어막이지만, 경계로 믿으면 안 된다는 것이 이 사례의 요지다.

**면접에서 말할 한 문장.** "AI가 규칙을 지켰기 때문에 안전했던 것과, 지키지 않아도 안전한 것은 다르다. 후자를 코드와 뮤테이션 테스트로 만들었다."

## 사례 2. 최소 권한 문서는 기능이 늘면 썩는다: "200 OK"는 통과가 아니었다

근거: [VERIFICATION 127절](VERIFICATION.md), [least-privilege.md](least-privilege.md)

**상황.** 5기종 모니터 계정의 최소 권한은 2026-07-04에 실측으로 확정해 문서와 init 스크립트에 박제했다.
그 뒤 대기 이벤트, 세션 블로킹, advisor, finops 기능이 추가됐다. 워크벤치가 조회·변경 계정을 따로 두려면
"모니터 계정이 무엇을 할 수 있는가"의 기준선이 먼저 맞아야 한다.

**문제.** 사례 1 라이브 검증 중 MySQL wait-events·sessions가 502였다. API 25개를 전부 부르니 502는 두 건뿐인데,
오퍼레이터가 읽는 테이블을 모니터 계정으로 직접 찔러 보니 누락은 **7개**였다. 두 개는 HTTP 200 응답 본문 안의
점검 항목만 `ERROR`였고, 나머지는 이 토폴로지에서 코드 경로를 타지 않았다.

**결정.**
- 기능 호출 결과가 아니라 원천 테이블 직접 조회로 누락을 확정한다.
- 부여 뒤 하나씩 회수해 최소성을 증명한다. `sys` 뷰는 INVOKER 뷰라 뷰 SELECT, 원천 테이블 SELECT, 뷰가 부르는 함수 EXECUTE가 모두 있어야 했다(단계별 에러 원문 기록).
- 관측으로 증명한 것과 코드 경로로만 확인한 것을 문서 표에서 구분한다.
- 재발 방지를 사람의 기억에 맡기지 않는다. "오퍼레이터가 읽는 테이블은 init 스크립트에 GRANT가 있어야 한다"를 빌드 규약 검사로 넣었다.

**검증 수치.** 5기종 × API 25개. MySQL 누락 7 → 0(부여 후 WARN 로그 0건), PostgreSQL·Oracle·MongoDB 누락 0.
SQL Server는 로컬 Colima(Rosetta 미사용)에서 amd64 이미지가 기동 즉시 죽어 측정하지 못했고, 사용자 VM 재시작이
필요한 조작이라 하지 않은 채 블로커로 기록했다.

**면접에서 말할 한 문장.** "상태 코드 200을 통과로 세면 권한 누락 7개 중 2개만 보인다. 원천 테이블을 직접 찔러 확정하고, 회수해서 최소성을 증명하고, 빌드가 재발을 막게 했다."

## 사례 3. "읽기 전용"을 쓰기 권한 계정으로 검증했다: 같은 JDBC 호출, 드라이버 셋, 동작 셋

근거: [VERIFICATION 128절](VERIFICATION.md)

**상황.** 사람이 자유 SQL로 대상 DB를 조회하는 거버넌스 워크벤치를 만들었다. Spider 2.0 기준 기업형 Text-to-SQL
정확도가 20%대라, 다음 단계에서 AI가 SQL을 제안하더라도 실행 경계는 AI와 무관하게 서 있어야 한다.

**결정.** 경계를 문자열 검사 하나에 걸지 않고 겹으로 쌓았다. 분류기(허용 목록) → 콘솔 계정 분리 → 읽기 전용 트랜잭션
(끝은 항상 롤백) → 결과 마스킹 → 컬럼 GRANT. 그리고 "겹이 있다"를 믿지 않고 **앞 겹을 전부 뺀 상태에서 다음 겹만으로
막히는지**를 겹마다 따로 쟀다.

**실측이 뒤집은 가정.**
- `Connection.setReadOnly(true)` 하나로 기종 분기 없이 된다고 봤다. 쓰기 권한 계정으로 INSERT를 넣어 보니 MySQL은 드라이버의
  텍스트 검사와 서버 플래그를 둘 다 걸었고, PostgreSQL은 서버가 `read-only transaction`으로 거부했고, **Oracle은 아무것도 하지
  않아 INSERT가 들어갔다**(끝의 롤백만 막고 있었다). Oracle에만 `SET TRANSACTION READ ONLY` 훅을 넣었다.
- 드라이버가 준 원래 컬럼명으로 마스킹하면 별칭을 막는다고 봤다. 라이브에서 **PostgreSQL `SELECT email AS e`가 원문 그대로**
  나왔다(pgjdbc는 원래 이름 자리에 별칭을 준다). 문장에서 별칭 쌍을 뽑아 원래 컬럼 규칙에 대도록 고쳤다.
- 이름 기반 마스킹은 `email || ''`을 원리상 못 막는다. 이걸 숨기지 않고 테스트로 "가려지지 않음"을 고정한 뒤, 본 방어선인
  **컬럼 GRANT가 같은 표현식을 `permission denied`로 막는 것**을 실측해 문서에 역할을 나눠 적었다.

**화면에서 잡은 것.** Playwright로 화면을 직접 눌러 보다가, `hidden` 속성의 모달이 CSS `display: flex`에 져서 로드 직후부터
실행 버튼을 가로막는 버그와, 로그인한 VIEWER가 ADMIN 경로를 부르면 403 대신 로그인 페이지로 튕기는 기존 버그(`/error` 재디스패치)를 잡았다.

**면접에서 말할 한 문장.** "읽기 전용이라고 쓰기 전에, 쓰기 권한 계정으로 INSERT를 넣어 봤다. 같은 표준 호출이 드라이버 셋에서 세 가지로 동작했고, 그중 하나는 아무것도 막지 않았다."

## 사례 4. AI에게 실행 권한을 주지 않고도 쓸 만하게: 제안 · 체크포인트 · 실행 결과로 잰 정확도

근거: [VERIFICATION 129절](VERIFICATION.md), [평가 러너](../scripts/eval-workbench-nl2sql.py)

**상황.** 사내 어드민 생성 플랫폼(TOI Studio) 화면을 보면 AI 대화가 "요청 → 계획 → 작업 → 체크포인트 카드"로 흐르고,
입력창의 선택 커서로 화면 요소를 찍어 요청에 붙인다. 이 경험을 DB 조회에 옮기되, AI가 대상 DB에 무엇도 실행하지 않게 하고 싶었다.

**결정.**
- AI는 **실행 도구가 없는 격리된 LLM**이다. SQL 텍스트만 내고, 그 텍스트는 사람이 실행할 때 1단계 경계(분류·조회 계정·읽기 전용·마스킹)를 다시 지난다.
  스키마·오류·대화에 지시문이 심겨도 AI가 할 수 있는 최악은 "사람이 읽을 이상한 SQL"이다.
- 제안마다 서버가 분류(읽기/승인 필요/차단)와 **스키마에 없는 테이블**을 표시한다. Uber QueryGPT가 사람 확인 단계로 풀던 환각 문제를 결정론적 대조로 먼저 걸렀다.
- 워크시트마다 대화와 SQL 버전을 **서버에** 쌓는다. 되돌리기도 새 버전이라 실행 기록과 이력이 어긋나지 않는다. 카드에는 만든 사람이 붙는다.
- 결과 값을 외부 LLM에 보낼지는 인스턴스별 ADMIN 설정이고, 꺼져 있으면 **AI 호출 전에** 거부한다.

**검증 수치.** 데모 스키마 12문항을 실행 결과로 채점해 lenient 12/12, strict 7/12(떨어진 5건은 전부 열을 더 붙인 경우),
안전 문항 2/2, 응답 중앙값 9.0초. 한계도 같이 적었다: 테이블 2개·1회 실행이라 기업 벤치마크와 비교할 수치가 아니며,
이 평가의 용도는 프롬프트·컨텍스트 변경의 전후 비교다.

**화면에서 확인한 흐름.** 질문 → 체크포인트 v1 → 미리보기 실행 → 선택 모드로 결과 열을 칩으로 → 후속 질문에 AI가 편집기 SQL과 칩을 이어받아 v2 제안 → 새로고침해도 복원.

**면접에서 말할 한 문장.** "AI에게 실행 권한을 주지 않았다. 대신 제안마다 분류와 환각 표시를 붙이고, 정확도는 AI가 낸 SQL을 실제로 실행한 결과로 쟀다."

## 사례 5. "승인된 변경만 실행한다"를 SQL 검사가 아니라 트랜잭션 불변식으로 보장하기

근거: [VERIFICATION 130절](VERIFICATION.md), [실행 흐름](../src/main/java/io/dbtower/operator/internal/JdbcChangeRunner.java),
[3기종 실DB 테스트](../src/test/java/io/dbtower/operator/internal/ChangeExecutionIT.java)

**상황.** 리뷰 게이트는 판정·승인까지만 했고, 실행은 사람이 DB 클라이언트로 따로 했다. 그러면 승인된 SQL과 실행된 SQL이 같다는
증거도, 되돌릴 사본도, 전후 비교도 남지 않는다. DBeaver 같은 도구는 실행은 쉽지만 이력이 없어 "이 변경 전후로 무엇이 달라졌나"를 못 보여준다.

**결정.**
- **상태의 단일 권위는 게이트다.** 실행 계층은 `where id = ? and status = 'APPROVED'` 조건부 UPDATE로만 실행권을 얻는다. 두 사람이 동시에 눌러도 대상 DB에는 한 번 닿는다.
- **안전은 파서가 아니라 불변식에서 나온다.** 사본 조회는 원문 WHERE를 그대로 붙일 뿐이다. 같은 트랜잭션에서 사본을 락과 함께 잡고,
  대상 DB가 보고한 영향 행 수가 사본 행 수와 같을 때만 커밋한다. 파서가 틀리거나 동시 변경이 끼면 커밋되지 않는다.
  다중 테이블·upsert처럼 사본을 확정할 수 없는 문장은 사람이 "캡처 없이 실행"을 명시해야만 나간다.
- **되돌리기는 SQL 문자열을 만들지 않는다.** JDBC 타입이 붙은 사본을 파라미터로 바인딩한다. 쓰기 전에 현재 행이 실행 직후 사본과 같은지
  락을 걸고 대조하고, 한 행이라도 다르면 아무것도 쓰지 않는다.
- **실패를 두 종류로 나눈다.** 대상 DB가 롤백을 확정한 실패는 다시 실행할 수 있게 실행권을 돌려주고, 커밋 호출 자체가 실패해 반영 여부를 모르면 돌려주지 않는다.
- **드라이런은 실제로 실행한 뒤 롤백한다.** 승인 전에 바뀔 행과, 커밋 전 인덱스가 반영된 실행계획을 같은 트랜잭션에서 본다.
  DDL이 암묵 커밋인 기종은 기종 분기가 아니라 드라이버 메타데이터(`dataDefinitionCausesTransactionCommit`)로 알아내 드라이런을 거부한다.
- **사본은 개인정보 원본이다.** 암호화 저장, 7일 뒤 파기, 화면은 마스킹(바뀌었는지 판정은 원래 값으로).

**검증 수치.**
- 실제 DB 3기종(MySQL 8.4, PostgreSQL 16, Oracle 23ai)에서 오퍼레이터만으로: 드라이런 뒤 행 불변, UPDATE·DELETE·INSERT를 되돌린 뒤
  원래 행과 DB가 찍은 문자열이 일치(따옴표·백슬래시·주입 모양 문자열·마이크로초·이진·jsonb 포함), 한 행 드리프트면 전부 미적용,
  사본 조회를 일부러 틀리게 준 계획은 커밋 0.
- 앱 API 라이브: 승인 뒤 동시 실행 2건 `[200, 409]`, 승인된 `TRUNCATE`는 422(분류기 재판정), PostgreSQL 인덱스 드라이런에서
  `Seq Scan -> Index Scan`(드라이런 뒤 인덱스 없음), 실행 뒤 구조 diff, 인스턴스 간 비교에서 등급 한 칸 차이만 짚음, VIEWER는 세 경로 모두 403.

**라이브에서 뒤집힌 가정 넷.** 단위 테스트가 전부 통과한 뒤 앱을 띄워 돌리자 넷이 나왔다.
(1) Spring Boot 4의 Jackson 3는 원시 `boolean`이 빠진 `{}` 본문을 거부해 드라이런·실행이 서비스에 닿기 전에 400이었다(서비스 테스트는 HTTP 바인딩을 안 거친다).
(2) PostgreSQL 15+는 테이블 소유자여도 스키마 `CREATE` 없이는 인덱스를 못 만든다(최소 권한 문서 수정).
(3) 실행 직후 워크로드 비교는 뒤 구간에 스냅샷이 없어 오류였다(상태로 돌려주게 수정).
(4) 되돌린 뒤에도 원래 실행 기록이 "되돌리기 가능"으로 남아 게이트가 거부할 버튼을 보여줬다.

**면접에서 말할 한 문장.** "승인된 변경만 플랫폼이 실행하게 했는데, 안전을 SQL 파싱에 걸지 않았다. 같은 트랜잭션에서 사본 행 수와
영향 행 수가 다르면 커밋하지 않고, 되돌리기는 실행 직후 사본과 지금 행이 같을 때만 쓴다."

## 사례 6. "완벽하게"를 목록이 아니라 실측으로: 남은 공백을 스스로 찾아 끝까지 닫기

근거: [VERIFICATION 131절](VERIFICATION.md)

**상황.** 3단계를 커밋한 뒤 "다 됐다"고 보고할 수 있었지만, 원래 요구와 코드를 다시 대조하자 공백이 나왔다. 사용자가 처음 말한
"클릭하면 테이블 창"이 없었고, 승인된 채 실행하지 않을 티켓을 닫을 방법도, 커밋 여부를 모르는 티켓을 풀 방법도 없었다.
SQL Server는 로컬에서 뜨지 않아 막아 뒀고, MongoDB 변경은 미지원, 성능 전후는 트래픽 없는 데모라 동작 확인뿐이었다.

**결정.**
- **사람의 출구를 상태 기계에 넣는다.** 취소는 대기·승인 상태에서만, 커밋 불명 정리는 사람이 대상 DB를 무엇으로 확인했는지 근거를
  적어야만 한다. 플랫폼이 다시 봐서 자동 판정하지 않는다 — "모른다"를 "안다"로 바꾸는 순간 두 번 실행의 위험이 생긴다.
- **막아 둔 기종은 먼저 재고 연다.** SQL Server는 arm64 Azure SQL Edge로, MongoDB는 로컬 복제셋으로 드라이버·엔진 동작을 구현 전에
  실측했다. 그 결과가 설계를 바꿨다: SQL Server는 락이 테이블 뒤 힌트라 사본 조회의 FROM과 WHERE를 나눴고, IDENTITY 열은 되돌려
  넣을 때 별도 설정이 필요했다. MongoDB는 트랜잭션 안에서 explain과 인덱스 생성이 거부돼 측정은 트랜잭션 밖, DDL 드라이런은 거부로 갔다.
- **에이전트 채널은 요청과 조회까지만.** MCP 도구는 변경 요청 올리기·상태 보기·조회 셋이고, 조회는 인스턴스의 "결과 값 AI 공유"
  설정이 켜진 경우만 연다. 드라이런·실행·되돌리기·승인은 도구로 만들지 않았다(드라이런도 실제로 실행하고 락을 잡는다).
- **성능 주장은 부하를 걸어 잰다.** 100만 행 결제 이벤트 표에 pgbench로 같은 부하를 인덱스 티켓 전후에 걸었다.

**검증 수치.**
- 실DB IT 5기종(MySQL·PostgreSQL·Oracle·SQL Edge·MongoDB) 실행·되돌리기·드리프트 충돌·불변식 위반 통과. SQL Edge DDL 드라이런은
  같은 트랜잭션 안에서 Clustered Index Scan -> Index Seek, MongoDB 인덱스 실행 뒤 COLLSCAN -> IXSCAN.
- 부하 기반 인덱스 티켓(pgbench 4클라이언트 120초씩): 평균 지연 49.634 ms -> 0.029 ms, 처리 9,672건 -> 16,402,198건.
  같은 구간을 플랫폼의 스냅샷 비교로 보면 그 쿼리가 49.31 ms -> 0.0 ms(표시 반올림), QPS 37.34 -> 68,116.99.
- 라이브: 요청자의 자기 승인 409(분리 옵션), 사본 암호화 저장(플랫폼 DB에 평문 이메일 없음, 화면은 복호화 뒤 마스킹),
  티켓마다 요청·승인·실행·되돌림 결과 카드 4건 발송.
- MCP 라이브: 도구 19종 중 실행 계열 이름 0, 에이전트가 올린 티켓은 PENDING에 머물고 대상 행 그대로, 결과 값 공유가 꺼진 인스턴스의
  조회는 대상 DB에 닿기 전 403, 켜면 마스킹된 행, 변경 문장 조회는 409, 팀 밖 사용자의 단건 티켓 조회는 404.

**측정의 한계를 같이 적었다.** pgbench는 DB 컨테이너 안에서 돌아 네트워크 왕복이 없고, 조회는 합계 한 줄짜리라 인덱스만으로 끝나는
가장 유리한 모양이다. 수치의 쓸모는 "이 플랫폼이 승인된 변경의 전후를 같은 부하로 재서 보여줄 수 있다"는 증거이지 일반적인 개선 폭이 아니다.
SQL Edge는 지원이 끝난 제품이라 실제 SQL Server 2022 검증을 대신하지 않는다. MCP로 올린 티켓의 요청자는 사람이 아니라 서비스 토큰으로 남는다.
(이 한계들은 사례 7에서 다시 파서 닫았다. 넷은 한계가 아니라 결함이었다.)

**면접에서 말할 한 문장.** "다 됐다고 말하기 전에 원래 요구와 코드를 다시 대조했고, 막혀 있던 기종은 구현 전에 드라이버 동작부터 재서
열었다. 성능 주장은 같은 부하를 인덱스 티켓 전후에 걸어 쟀다."

## 사례 7. 한계로 적은 것을 다시 파 보니 결함이었다: 요청자 신원, 행 지표의 뜻, 표시 정밀도

근거: [VERIFICATION 132절](VERIFICATION.md)

**상황.** 사례 6을 마치며 한계를 정직하게 적어 두었다. SQL Server는 SQL Edge로만 검증했고, MCP로 올린 티켓의 요청자는 서비스 토큰으로
남으며, 성능 비교는 0.0 ms로 반올림되고 "스캔 행 +706%"는 해석이 필요하다고. 사용자가 "남은 한계도 다 해줘"라고 했다. 한계 목록을
다시 코드로 따라가 보니 넷은 환경이나 측정의 한계가 아니라 제품이 틀린 것이었다.

**찾은 것.**
- **요청자 신원이 채널에서 바뀌었다.** MCP HTTP 전송이 모든 도구 호출을 서비스 토큰으로 REST에 위임했다. 관리자가 OAuth로 MCP에
  들어와 변경 요청을 올리면 요청자가 `api-token`으로 기록됐고, 같은 사람이 화면에서 자기 요청을 승인하는 것을 요청자·승인자 분리가
  막지 못했다. 수정 전 코드를 따로 띄워 재현했다: MCP 경로 승인 200, 같은 토큰의 REST 경로 409.
- **처음 의심은 틀렸다.** 역할·팀 범위도 넓어진다고 봤는데, VIEWER 토큰으로 재 보니 `/mcp` 체인이 ADMIN 전용이라 403이었다.
  넓어진 것은 범위가 아니라 신원이었다. 코드 주석과 문서를 실측에 맞춰 고쳐 적었다.
- **같은 이름에 다섯 가지 단위.** 누적 통계의 "읽은 행수" 자리에 MySQL은 검사한 행, PostgreSQL은 돌려준 행, SQL Server는 논리 읽기
  페이지, Oracle은 버퍼 블록, MongoDB는 검사한 문서가 들어왔다. 회귀 알림은 PostgreSQL의 결과 크기 증가를 "플랜 변화 의심"으로 적었다.
- **표시가 사실을 지웠다.** 평균 레이턴시 0.0036 ms가 소수 둘째 자리 반올림으로 0.0이 됐고, 워크벤치는 UTC 시각을 그대로 찍어
  "앱과 셸 시계가 9시간 다르다"는 잘못된 해석을 낳았다.

**결정.**
- **채널은 신원을 바꾸지 않는다.** 위임 토큰은 그 요청을 인증한 호출자의 것을 그대로 쓴다. 원칙으로 AGENTS.md와 DESIGN에 적었다.
- **단위의 뜻은 기종 오퍼레이터가 답한다.** `rowsMetric()`을 기본값 없이 인터페이스에 더해 새 기종이 이 질문을 건너뛰지 못하게 했다.
  화면·알림·MCP 도구 설명이 같은 이름을 쓰고, "돌려준 행" 기종에서는 플랜 변화로 적지 않는다.
- **막힌 환경은 다시 확인한다.** "Rosetta 없음"은 128절 시점의 사실이었다. 지금 Mac에는 Rosetta가 있어 기존 VM을 건드리지 않고
  Rosetta VM을 하나 더 띄워 실제 SQL Server 2022에서 IT와 라이브 흐름을 다시 돌렸다. 포트 충돌(Ollama)도 응답 바이트 72(`H`)로 짚었다.

**검증 수치.**
- 요청자·승인자 분리: MCP 경로 자기 승인 수정 전 HTTP 200 APPROVED -> 수정 뒤 409, 요청자 `api-token` -> `admin`.
- SQL Server 2022 RTM-CU26: 엔진 동작 표·계정 권한 결과가 SQL Edge와 한 줄도 다르지 않았고, 라이브 M0~M6(IDENTITY 재삽입 복원 같음,
  계획 Clustered Index Scan -> Index Seek, 권한 밖 DROP TABLE 422) 통과.
- Oracle 앱 스키마: 모니터 계정의 스키마 트리가 빈 목록 -> `[CHANGE_IT, CONSOLE_RO_PROBE, CUSTOMERS, USERS]`, 소유자 없는 이름의 티켓이
  드라이런·실행·되돌리기까지.
- 같은 스냅샷을 다시 조회: 49.31 ms -> 0.0 ms 표시가 48.9453 ms -> 0.0036 ms로.
- 측정 경로를 바꿔 다시 쟀다: 호스트 pgbench(포트 포워딩 TCP)와 행 20건을 돌려주는 조회로 평균 지연 46.378 ms -> 0.521 ms(약 89배).
  같은 인덱스 티켓을 컨테이너 안·합계 조회로 잰 사례 6은 약 1,700배였다. 서버 안 실행 시간은 0.0325 ms까지 줄었지만 클라이언트가 보는
  지연은 왕복 비용에 막힌다 — 개선 폭을 크게 말할 수 있던 수치를 스스로 줄여 적었다.

**면접에서 말할 한 문장.** "한계 목록도 검증 대상으로 봤다. 다시 파 보니 채널이 요청자 신원을 서비스 토큰으로 바꿔 승인 분리를
비껴가고 있었고, 수정 전 코드를 따로 띄워 200을 재현한 뒤 409로 닫았다."

## 사례 8. "이 Mac에서도 방법이 있을 것"을 조사로 확정하고, 없는 것 대신 잴 수 있는 것을 쟀다

근거: [VERIFICATION 133절](VERIFICATION.md)

**상황.** 사례 7에서 제약 셋을 남겼다. SQL Server 2022는 Rosetta 위의 x64 번역이라 µs를 성능 근거로 못 쓰고, Oracle 앱 스키마는 앱 전역 하나이며,
pgbench 클라이언트와 DB가 같은 Mac을 쓴다. 사용자는 "이 Mac에서도 네이티브 x64로 돌릴 방법이 있을 테니 자세히 찾아보라"고 했다.

**조사와 결정.**
- **"안 된다"에도 근거를 붙인다.** Microsoft 문서의 문장("supported only on Linux hosts running on Intel and AMD x86-64 CPUs. Emulation or translation
  environments (for example, Rosetta 2, Prism, or QEMU) aren't tested or supported"), ARM 컨테이너 지원 요청 이슈, Rosetta의 AVX 처리(SQL Server 2025 RTM
  기동 실패, CU1에서 수정), Apple `container`·OrbStack·Parallels+Prism까지 경로마다 실제 실행 방식을 표로 정리했다. 모든 경로가 번역이나 에뮬레이션이었다.
  네이티브 x64 수치가 필요하면 다른 하드웨어(Azure SQL Database 무료 제공, GitHub Actions x64 러너)가 필요하고, 계정·push는 사용자 결정으로 남겼다.
- **없는 것 대신 번역 비용을 잰다.** SQL Server는 arm64 빌드가 없어 직접 비교할 수 없으니, arm64·amd64 빌드가 둘 다 있는 PostgreSQL 16을 같은 Rosetta VM에서
  같은 pgbench로 맞붙였다. 번역이 DB 엔진 모양의 작업을 얼마나 느리게 하는지가 나왔고, 그 수치를 환산 계수로 쓰지 않는다는 선도 같이 적었다.
- **해석을 측정으로 바꾼다.** 사례 7에서 "인덱스 뒤 남은 지연은 왕복 비용"이라고 설명했던 것을, 서버가 거의 일하지 않는 `SELECT 1`을 경로만 바꿔 보내 확인했다.
- **전역 설정 하나를 인스턴스 등록값으로.** Oracle 앱 스키마를 인스턴스별로 등록하게 하고(V39), 전역 설정은 등록값이 없을 때의 기본값으로 내렸다.

**검증 수치.**
- Rosetta 번역 비용(같은 VM·같은 이미지 태그·arm64 대 amd64): 조회 전용 166,915 -> 117,841 tps(0.71배), TPC-B 6,175 -> 4,222 tps(0.68배).
- 경로 분해(`SELECT 1`): 컨테이너 안 0.018 ms, 호스트 TCP 0.539 ms — 사례 7의 인덱스 뒤 클라이언트 지연 0.521 ms와 같은 크기.
  다른 VM에서 호스트를 거쳐 오면 0.664 ms. 같은 Mac 하나로 "다른 호스트" 수치는 만들 수 없다는 선을 넘지 않았다.
- Oracle 앱 스키마 인스턴스별: 같은 Oracle을 두 이름으로 등록해 스키마 트리 [] 대 [CHANGE_IT, CONSOLE_RO_PROBE, CUSTOMERS, USERS],
  콘솔 조회 ORA-00942 대 성공. 식별자가 아닌 값은 400, 값을 빼면 즉시 미지정 동작으로 돌아간다.

**면접에서 말할 한 문장.** "안 된다는 결론도 근거가 있어야 한다. 공식 문서 문장과 이슈로 네이티브 경로가 없음을 확정하고, 대신 같은 VM에서 arm64와 amd64를
맞붙여 번역이 DB 처리량을 약 0.7배로 만든다는 것을 쟀다."

## 사례 9. 네이티브 x64로 재고, 정리하다 찾은 결함을 고치고 합친다: 말 없는 대상 하나가 폴러 전체를 멈췄다

근거: [VERIFICATION 134절](VERIFICATION.md), [PR #2](https://github.com/dj258255/dbtower/pull/2)

**상황.** 사례 8에서 "이 Mac에서는 SQL Server를 번역 없이 돌릴 수 없다"를 확정하고 다른 하드웨어 경로를 사용자 결정으로 남겼다. 사용자가 "다 해줘"라고 해
브랜치를 push하고 PR을 열어 GitHub의 x64 러너에서 같은 IT와 같은 부하 측정기를 돌렸다. 측정이 끝나고 검증용 등록을 지우던 중 삭제 API가 돌아오지 않았다.

**결정.**
- **같은 측정기를 양쪽에서.** SQL Server에는 pgbench가 없어 JDBC 측정기를 저장소에 두고, Rosetta VM과 x64 러너에서 같은 순서로 돌렸다. 클라이언트 지연과
  서버 실행 시간(`dm_exec_query_stats`)을 같이 찍어 경로 비용을 떼어 봤다.
- **CI 실패를 추측으로 덮지 않는다.** 첫 x64 실행이 5분 동안 멈췄을 때 "Ubuntu 24.04에서 SQL Server 컨테이너가 죽는 알려진 문제"를 먼저 의심했다. 로그를 받아 보니
  원인은 우리 워크플로(`compileTestJava`가 런타임 JDBC 드라이버를 받지 않음)였다. 틀린 가설을 그대로 적고 고쳤다.
- **멈춘 삭제를 스레드 덤프로 읽는다.** 삭제된 VM의 포트 포워드가 연결만 받고 말이 없자, SQL Server 풀 생성의 첫 연결이 prelogin 읽기에 매달렸다. 그 생성이
  `ConcurrentHashMap.computeIfAbsent` 안이라 운영 경보·헬스 스코어·설정 드리프트 폴러와 삭제 API가 같은 락 뒤에 줄을 섰다. 폴러는 인스턴스를 차례로 돌므로 대상
  하나가 전체 관제를 멈춘다. 우연히 만난 환경 문제가 아니라 "대상 장애가 플랫폼을 죽이면 안 된다"를 어기는 제품 결함으로 보고, 연결만 받는 소켓 서버로
  재현 테스트를 먼저 만들었다(수정 전 SQL Server·Oracle 25초 초과).
- **긴 작업을 끊지 않는 선에서 막는다.** 로그인 단계에만 읽기 제한을 걸고 로그인이 끝나면 푼다. 같은 커넥션 경로로 서버 사이드 BACKUP·RESTORE·Data Pump가
  돌기 때문이다. 풀 생성은 첫 연결을 붙잡지 않게 늦췄다.

**검증 수치.**
- 네이티브 x64(SQL Server 2022 RTM-CU26): IT 전부 통과. 인덱스 전후 서버 실행은 러너 두 번에 53,052 -> 75.1 µs, 122,541 -> 173.0 µs로
  두 배 넘게 흔들렸다(Rosetta VM 70,858 -> 145.0 µs). 첫 실행만 보고 "Rosetta가 1.3~1.9배 느리다"고 적었던 해석을 두 번째 실행이 뒤집어 거뒀다.
  흔들리지 않은 것은 실행계획과 논리 읽기(3,973 -> 63, 세 실행 모두 같음) — 엔진이 한 일은 같고, 공유 러너의 µs는 환경 비교 근거가 못 된다.
- 말 없는 대상 재현 테스트: 수정 전 SQL Server·Oracle 헬스체크 25초 초과(매달림), 같은 인스턴스의 두 번째 호출도 25초 초과 -> 수정 뒤 4개 JDBC 기종
  모두 약 2초(테스트 풀의 connectionTimeout)에 down, 매달린 첫 연결 뒤 풀 정리 1ms.
- 로그인 뒤 제한 해제: 풀 커넥션으로 서버 7초 대기 SQL Server 7,005 ms·Oracle 7,019 ms 끝까지 받음(networkTimeout=0) — 긴 백업 경로를 끊지 않는다.

**면접에서 말할 한 문장.** "측정을 끝내고 정리하다 삭제 API가 멈췄다. 스레드 덤프로 보니 말 없는 대상 하나가 풀 생성 락을 쥐고 모든 대상의 폴러를 세우고 있었고,
연결만 받는 소켓 서버로 재현한 뒤 긴 백업은 끊지 않는 선에서 로그인 단계만 막았다."

## 사례 10. 한 플랫폼, 사람별 입구: 제품을 나누지 않고 쓰는 사람을 나눴다

근거: [VERIFICATION 135절](VERIFICATION.md), [DESIGN 3.6](DESIGN.md)

**상황.** 워크벤치가 커지자 사용자가 물었다. "거버넌스 SQL 워크벤치와 이기종 DBMS 관제를 섞으면 안 되나, 쓰는 사람을 명확히 해야 할 것 같다." 코드를 보니 문제는 화면이
두 개라는 데 있지 않았다. 역할이 VIEWER·ADMIN 둘뿐이라 인가 경계 24개가 전부 ADMIN이었고, 백업을 돌리는 DBA는 인스턴스 등록·보안 설정까지 함께 받아야 했다. 관제만 보면
되는 사람도 워크벤치로 대상 DB의 행 값을 봤고, 변경을 승인하는 사람과 실행하는 사람이 같은 ADMIN이었다.

**결정.**
- **제품은 하나로 둔다.** 두 화면은 인스턴스·팀 범위·감사·변경 티켓·AI 진단을 공유하고, 운영자의 한 흐름(관제에서 이상 -> 데이터 확인 -> 변경 요청 -> 실행 뒤 전후 확인)이
  둘을 오간다. 나누면 이 흐름이 시스템 경계를 넘어 인증·범위·감사를 두 번 맞춰야 한다. 대신 역할을 쓰는 사람 기준 다섯으로 나눴다.
- **승인자와 운영자는 서로를 포함하지 않는다.** 계층은 ADMIN이 둘을 모두 갖고, 둘은 REQUESTER를, REQUESTER는 VIEWER를 포함한다. 자기 승인을 이름으로 막는 설정(기본 꺼짐)과 달리
  역할 분리는 설정과 무관하게 승인과 실행을 다른 사람에게 둔다.
- **화면은 역할 이름이 아니라 능력으로 가른다.** `/api/me`가 같은 계층으로 계산한 capabilities를 주고, 버튼은 `CHANGE_APPROVE`·`CHANGE_EXECUTE` 같은 능력으로 분기한다.
  인가와 화면이 같은 정의(`PlatformRoles`)를 읽으니 역할이 늘어도 화면 분기는 그대로다.
- **기존 사용자의 권한을 조용히 빼앗지 않는다.** VIEWER의 뜻을 "관제만"으로 좁히면서, 워크벤치를 쓰던 기존 VIEWER는 마이그레이션이 REQUESTER로 옮긴다.
- **입구를 닫는 대신 위임을 믿는다.** MCP 채널은 입구에서 ADMIN만 받았는데, 도구 호출이 호출자 토큰으로 REST에 위임되므로(사례 7) 입구를 관제부터 열고 판정은 REST에 맡겼다.
- **로그인 뒤 첫 화면은 역할로, 단 가려던 곳이 먼저.** 요청자는 워크벤치, 나머지는 대시보드. 알림 딥링크·OAuth 인가처럼 저장된 요청이 있으면 그곳으로 가되, 쿼리 없는 루트는 버린다.
- **넘김은 세 곳만.** 쿼리 상세 -> 워크벤치 새 워크시트, 인덱스 제안 -> 변경 요청 창(가상 인덱스 비용을 사유로), 실행 기록 -> 대시보드 전후 시점 비교. SQL은 URL 대신
  localStorage에 한 번 쓴다(수 KB 쿼리가 요청 줄 상한 8KB를 넘기 때문).

**검증 수치.**
- 인가 경계 분포: ADMIN 24 -> ADMIN 9 · OPERATOR 12 · APPROVER 2 · 승인자·운영자 공통 1(드라이런) · REQUESTER 2 · VIEWER 1(MCP 입구).
- 테스트 24건 추가(757 -> 781, 실패 0): 역할 행렬 MockMvc, 계층·능력 정의, 로그인 성공 처리(저장된 요청 재생·루트 무시), 마지막 ADMIN 잠김 방지.
- 라이브 실DB(MySQL) 한 티켓: 요청 p-requester -> 요청자 승인 시도 403 -> 승인자 드라이런(1행, 롤백)·승인 -> 승인자 실행 시도 403 -> 운영자 실행(1행 커밋)·되돌리기.
  기록에 요청·승인·실행·되돌리기가 세 사람으로 남았다.
- 로그인 착지: 요청자 `/workbench.html`, 나머지 `/`. 로그인 전에 연 `/workbench.html?instance=2&ticket=1`은 운영자 로그인 뒤 그대로 재생, 쿼리 없는 `/`는 요청자를 워크벤치로.
- MCP: 관제 토큰도 도구 19종 목록을 받지만 변경 요청 도구는 REST 403, 요청자 토큰은 요청자 이름으로 티켓 생성.
- 테스트가 틀린 곳도 기록했다. 저장된 요청 재생을 MockMvc로 확인하다 두 번 실패했는데, TRACE 로그로 서버는 저장했고 테스트의 세션이 달랐음을 확인한 뒤 성공 처리기 단위 테스트와
  실제 쿠키 세션 라이브로 나눠 확인했다. 화면은 뒤이어(136절) 역할별 로컬 프록시가 세션을 들고 브라우저는 로그인하지 않는 방식으로 다섯 역할을 모두 눌러 봤고,
  그 과정에서 결함 둘(관제 역할의 워크벤치 안내가 레이아웃 첫 칸에 끼어 세로로 늘어짐, 대시보드 리뷰 카드의 승인 시각이 UTC 원문이라 워크벤치와 9시간 어긋남)을 찾아 고쳤다.

**면접에서 말할 한 문장.** "관제와 워크벤치를 나눌지 물었을 때 화면이 아니라 사람을 나눴다. 역할 둘로는 백업하는 DBA가 보안 설정까지 가져야 했고 승인한 사람이 곧바로 실행할 수 있었는데,
승인자와 운영자가 서로를 포함하지 않는 계층 하나로 인가와 화면을 같이 갈랐다."

## 사례 11. 기다림을 보이게: 관측이 부하가 되지 않는 실시간, 판단을 바꾸지 않는 스트리밍

근거: [VERIFICATION 140절](VERIFICATION.md)(실시간 관제), [141절](VERIFICATION.md)(AI 스트리밍)

**상황.** 남은 일로 실시간 관제를 꼽자 사용자가 "이미 만들지 않았나"고 물었다. 확인해 보니 없었다. 비슷한 ASH 샘플러는 기본 꺼짐·PostgreSQL 전용으로 1초 샘플을 메타 DB에
쌓는 사후 분석용이었고, 화면은 인스턴스를 고를 때 세션을 한 번 읽고 끝이었다. AI 쪽도 같았다. 워크벤치 AI 제안과 자연어 진단은 답이 다 만들어질 때까지 10~20초(진단은 수십 초~분)
빈 말풍선이나 "진단 중..." 한 줄만 보였다. 둘 다 "기다리는 동안 무엇이 일어나는지 모른다"는 문제였다.

**결정.**
- **실시간은 브라우저 폴링이 아니라 서버 허브로.** 화면마다 2초 폴링하면 대상 조회가 보는 사람 수만큼 늘고, 장애 때 모두가 같은 대상을 열어 관측이 곧 부하가 된다(A9 원칙).
  대상마다 채널 하나가 주기마다 한 번 조회해 구독자 전원에게 SSE로 나누고, 구독자가 0이면 조회를 멈춘다.
- **WebSocket이 아니라 SSE.** 흐름이 서버에서 화면으로 한 방향이고, 평범한 GET이라 세션 쿠키·역할 인가·팀 스코프를 그대로 탄다. 연결 수명(5분)을 두어 재연결이 곧 재인가가 되게 했다.
- **실패도 프레임으로.** 조회 실패는 ERROR, 삭제는 GONE 프레임. 조용히 비우면 화면은 "세션 0건"과 "못 쟀다"를 구분하지 못한다.
- **안 보면 끊는다.** 탭이 숨었거나 카드가 안 보이는 그룹이면 연결을 닫는다. 안 보는 화면이 구독자로 남으면 허브를 둔 의미가 없다. 표 위에 포인터가 있으면 kill 버튼 오클릭을 막으려 표 갱신만 미룬다.
- **AI 스트리밍은 형식을 버리지 않는다.** 워크벤치 AI는 JSON 하나로 답해야 SQL·가정·제목을 나눠 저장할 수 있다. 토큰을 그대로 흘리면 사람은 따옴표를 읽게 되므로,
  미완성 JSON에서 설명·SQL 값의 앞부분만 뽑아 보여주고(`PartialJson`), 저장·분류·버전은 완성본을 다시 파싱해 만든다. 흘린 조각이 틀려도 남는 답은 바뀌지 않는다.
  max_tokens 절단 판정과 토큰 계수도 완성본에서 동기 경로와 같은 규칙으로 한다.
- **진단은 글자가 아니라 단계를 흘린다.** 진단 루프의 답은 도구 호출 결정 JSON이라 글자는 의미가 없고, 사람이 궁금한 것은 "지금 몇 번째 판단이고 무엇을 불렀나"다.
- **작업 스레드에 인증을 싣는다.** 스트림 작업은 요청 스레드 밖에서 돈다. 팀 범위·워크시트 소유·감사 주체가 SecurityContext에서 나오므로 제출 순간의 컨텍스트를 실어 보낸다.
  안 실으면 작업은 폴러와 같은 전역 주체로 돌아 팀 범위가 풀린다. 자리가 없으면 줄 세우지 않고 503 — AI 한 턴은 수십 초라 대기열 뒤의 사람은 멈춘 것과 구분하지 못한다.
- **API와 CLI 두 경로를 같은 규칙으로.** API는 SDK 스트리밍 + 누적기로 완성본을 다시 조립하고, 구독 기반 CLI는 `stream-json --include-partial-messages` 줄을 읽어 최상위 대화의
  text_delta만 흘린다. SDK의 클래스·메서드는 추측하지 않고 실제 jar(anthropic-java 2.34.0)를 javap로 열어 확인했다.

**검증 수치.**
- 실시간: 대상 PostgreSQL의 `pg_stat_statements`로 잰 30초 세션 조회 — 브라우저 각자 폴링 1·5·10명 15·76·150회, 허브 16·14·14회, 전원 떠난 뒤 0회. 앱 계수가 아니라 대상이 받은 값이다.
- 워크벤치 AI(claude CLI, 같은 질문 셋): 흘려 받을 때 첫 설명·SQL이 보이기까지 4.45·10.01·4.55초, 완성본 10.85·19.96·12.10초.
  한 번에 받을 때는 완성본이 올 때까지 아무것도 안 보인다(9.18·16.38·15.99초). AI 응답 시간 자체는 호출마다 흔들려 두 방식의 완성 시간 차이는 의미 있게 비교하지 않았다.
- 자연어 진단(앱 직접): 0.04초에 첫 판단 시작, 6.38초에 첫 도구(query_stats), 16.94·34.10초에 다음 도구, 108.16초에 결과. 동기 경로라면 108초 동안 한 줄이다.
  이벤트 8개 모두 JSON으로 읽혔다.
- 테스트: 실시간 허브 단위 9·SSE 입구 통합 3·실제 톰캣 경로 E2E 1, 미완성 JSON 추출 5(모든 잘림 위치에서 완성본의 접두사), CLI stream-json 줄 해석 4, 조각 중계·진행 알림 순서 5.
- 계측이 틀린 곳도 기록했다. 실시간 프레임 수가 전부 1로 나온 것은 계측 스크립트의 소켓 타임아웃 탓이었고, 진단 스트림의 JSON이 깨진 것은 역할 프록시가 chunked 청크 크기 줄을 본문에 섞은 탓이었다.
  둘 다 앱이 아니라 측정 도구의 결함이라, 고친 뒤 다시 재고 앱에 직접 붙어 모든 이벤트가 JSON으로 읽히는지 확인했다.

**면접에서 말할 한 문장.** "실시간과 스트리밍을 붙이면서 두 가지를 지켰다. 보는 사람이 늘어도 대상 DB 조회는 늘지 않아야 하고(10명 기준 150회에서 14회), 흘려 보여주는 AI 조각은
판단을 바꾸지 않아야 한다(저장은 완성본으로). 기다림을 보이게 하는 기능이 새 부하나 새 오류 경로가 되면 안 됐다."

## 사례 12. 동작이 맞아도 리뷰가 깨지면 품질 결함이다: 원시 NUL 바이트 사건

근거: [VERIFICATION 154절](VERIFICATION.md), [규약 검사](../scripts/check-conventions.sh)

**상황.** 153절 커밋 통계에서 Java 소스 하나가 줄 단위 diff가 아니라 `Bin 8425 -> 9147 bytes`로 찍혔다.
동작은 정상이었고, 150~153절 테스트 859개와 E2E 7/7도 통과했다. 하지만 git이 파일을 바이너리로 보면 PR에서 사람이 변경을 읽을 수 없고,
`grep "group:views"`도 실패한다. 리뷰와 검색이 깨진 것이다.

**원인.** 맵 키 구분자로 NUL을 쓰려다 `\u0000` 이스케이프 표기가 아니라 실제 NUL 한 바이트가 소스에 들어갔다.
Java 파일에는 150·151절 구간의 제약 키 조립 위치에, JS 파일에는 스키마 트리의 뷰 그룹 키에 들어 있었다.

**결정.**
- 값의 의미는 유지한다. 키는 계속 NUL로 시작하지만, 소스 파일에는 실제 제어 문자를 쓰지 않고 `\u0000` 이스케이프로 적는다.
- 사람이 조심하는 규칙으로 두지 않는다. 추적 파일(이미지·jar 제외)에 원시 NUL 바이트가 있으면 `scripts/check-conventions.sh`가 실패하게 했다.
- 문서 작성 중에도 같은 위험이 재현됐으므로, 초안이 아니라 커밋되는 파일 전체를 검사 대상으로 둔다.

**검증 수치.**
- 탐침 전 현재 상태: 규약 검사 통과.
- NUL 한 바이트를 심은 탐침 파일: 규약 검사 실패, `docs/nul-probe.txt: NUL 1개`.
- 탐침 제거 뒤: 규약 검사 통과, 추적 파일 전수 검사 NUL 0(이미지·jar 제외).

**면접에서 말할 한 문장.** "동작이 맞아도 PR diff와 grep이 사라지면 팀이 코드를 검토할 수 없다. 그래서 제어 문자를 쓰는 방식 하나도 빌드 규약으로 막았다."
