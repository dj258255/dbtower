# 대량 일괄 변경 — 설계와 안전 기준

승인된 티켓으로 **수십만~수백만 행**을 고치는 실행 방식을 정한다. 지금의 변경 실행(행 사본 방식)을 키우는 대신
별도 방식을 두는 이유와, 되돌리기를 무엇으로 보장하는지가 이 문서의 핵심이다.

관련 이슈: #101(이 명세)·#102(실행기)·#103(실행 전 조건·티켓)·#104(진행률·화면)·#105(100만 행 실측).

## 왜 지금 방식을 키우지 않는가

현재 `ChangeExecutionService`는 변경 전 행을 사본으로 떠 두고(`dbtower.workbench.change.max-rows`, 기본 10,000행)
영향 행 수를 대조한 뒤 커밋하며, 되돌리기는 그 사본으로 만든 역문장으로 한다. 이 방식의 안전은 **한 트랜잭션**에서 나오고,
그 대가가 행 수에 비례한다. 실측(`docs/experiments/change-lock-modes.md`, 2026-09-17):

| 기종 | 대상 행 | 방식 | 락 보유 중앙값 | 동시 작성자 p95 |
|---|---|---|---|---|
| PostgreSQL | 1,000 | PESSIMISTIC | 10.2ms | 1.0ms |
| PostgreSQL | 10,000 | PESSIMISTIC | 67.1ms | 1.1ms |
| PostgreSQL | 10,000 (작성자 쉼 50ms) | PESSIMISTIC | 81.8ms | 69.4ms |
| MySQL | 10,000 | PESSIMISTIC | 75.2ms | 1.8ms |
| MySQL | 10,000 (작성자 쉼 50ms) | PESSIMISTIC | 94.9ms | 86.6ms |

행 10배에 락 보유가 6~7배로 늘고, 동시 쓰기가 있으면 남의 쓰기 p95가 69~87ms까지 밀린다. 100만 행이면 같은 방식으로
수 초~수십 초를 한 트랜잭션이 쥔다. 게다가 한 트랜잭션의 대량 변경은 복제를 한꺼번에 밀어(binlog·WAL 한 덩이)
읽기 복제본이 뒤처진다. 그래서 대량은 **잘게 쪼개 커밋하는 별도 실행기**로 간다.

되돌리기도 같은 이유로 방식이 달라진다. 100만 행의 사본을 플랫폼에 저장하는 것은 되돌리기 보장이 아니라
또 하나의 데이터 사본 관리 문제다. 대량 변경의 되돌리기는 **복원 검증에 성공한 최근 백업**으로 보장한다.

## 실행 방식

### 기본 키 범위 배치

대상을 `WHERE` 조건으로 한 번에 고치지 않고, 기본 키 구간으로 나눠 구간마다 따로 커밋한다.

```sql
-- 배치 하나 (키가 비연속이어도 누락·중복이 없다)
UPDATE t SET ... WHERE <원래 조건> AND id > :lastKey AND id <= :nextKey
```

- `nextKey`는 행 수를 세지 않고 키를 훑어 정한다 — `SELECT id FROM t WHERE id > :lastKey ORDER BY id LIMIT 1 OFFSET :batchSize`가 없으면
  마지막 키를 끝으로 본다. 빈 구간은 문장을 보내지 않고 건너뛴다
- 조건은 승인된 문장의 `WHERE`를 그대로 두고 키 범위만 `AND`로 덧붙인다 — 파서가 조건을 다시 쓰지 않는다
- 복합 키는 사전순 비교(`(a, b) > (:a, :b)`)로 같은 성질을 유지한다(#126 구현). 열마다 부등호를 따로 쓰면
  구간이 겹치거나 비어 누락·중복이 생긴다 — 한 덩이로 비교해야 "이 키보다 뒤"가 하나의 뜻이 된다.
  열 수 상한은 3이다: 사전순 비교는 열 수와 무관하게 성립하지만, 경계 조회가 인덱스를 타는지는 기종·통계에 따라 갈린다
- 키가 없는 테이블(PK 없음)은 **거부한다** — 배치 경계를 정할 수 없으면 누락·중복을 막을 수 없다

### 배치 크기와 쉬는 간격

기본값은 배치 1,000행 · 쉼 100ms로 두고 티켓에 고정한다. 근거는 위 표다 — 1,000행 구간의 락 보유가 10~14ms이고,
그 정도면 동시 작성자 p95가 1ms대에 머문다. 쉼은 복제·purge가 따라오는 시간을 준다. 두 값 모두 승인 대상에 넣어
실행자가 승인 뒤에 바꿀 수 없게 한다(#103).

### 복제 지연 감시와 자동 멈춤·재개

배치마다 `DbmsOperator.replicationState()`를 읽는다.

- `lagSource == MEASURED`이고 `lagSeconds`가 임계(기본 5초)를 넘으면 **PAUSED_LAG**로 멈춘다. 임계 아래로 내려오면 재개한다
- `lagSource != MEASURED`면(못 재는 기종·지금 못 읽음) 지연으로 멈추지 않고, 그 사실을 배치 기록에 남긴다.
  "못 잰다"와 "지연 0"을 같은 값으로 쓰지 않는다(`ReplicationState` 주석의 규율)
- 복제가 끊긴 신호(MySQL `Seconds_Behind_Source` NULL)는 지연이 아니라 **중단**으로 본다 — 사람이 재개해야 한다

## 상태 전이

승인 티켓의 권위는 그대로 `ChangeTicketGate`에 둔다(`APPROVED -> EXECUTING -> EXECUTED`). 대량 실행은 그 안에서
배치 진행 상태를 따로 들고, 실행권은 조건부 UPDATE로만 얻는다.

```text
APPROVED -> EXECUTING -> EXECUTED            정상 완주
EXECUTING -> PAUSED_LAG -> EXECUTING         복제 지연으로 멈췄다 재개
EXECUTING -> PAUSED_BY_USER -> EXECUTING     사람이 멈췄다 재개
EXECUTING -> CANCELLED                       사람이 취소. 커밋된 배치는 남는다(아래 참조)
EXECUTING -> FAILED                          배치가 실패해 더 진행하지 않는다
```

**취소·실패는 이미 커밋한 배치를 자동으로 되돌리지 않는다.** 대량 변경은 부분 적용이 정상 상태다. 취소하면
"어디까지 적용됐는가"를 마지막 키로 남기고, 되돌리려면 사람이 백업 복원 경로로 판단한다. 조용히 역문장을 돌려
절반만 되돌리는 쪽이 더 위험하다.

## 실행 전 조건 (하나라도 어기면 거부)

1. **복원 검증에 성공한 최근 백업** — `BackupFreshness.verifyStatus == "VERIFIED"`이고 `status == FRESH`.
   `UNSUPPORTED`·`FAILED`·`NO_BACKUP`·`STALE`는 거부한다. 되돌리기를 백업에 맡기므로 이것이 이 기능의 전제다
2. **기본 키가 있는 단일 테이블** — 조인 대상 변경, PK 없는 테이블은 거부
3. **지원 문장** — `UPDATE`, `DELETE`, `INSERT ... SELECT`. 그 밖은 거부
4. **지원 기종** — MySQL·PostgreSQL 먼저. 나머지는 Operator에 능력이 붙을 때까지 거부
5. **승인 시점에 고정된 값** — 예상 영향 행 수, 배치 크기, 쉬는 간격, 복제 지연 임계. 승인 뒤 변경 불가
6. **예상 영향 행 수와 실제의 괴리** — 실행 시작 시 다시 센 수가 승인 시점의 2배를 넘으면 멈추고 재승인을 요구한다

## 기록

배치마다 처리한 키 범위(시작·끝), 영향 행 수, 걸린 시간, 그 시점의 복제 지연과 `lagSource`를 남긴다(#104).

## 여러 테이블에 걸친 변경 — 담을 수 없다 (#129 판정)

### 판정: 담을 수 없다. 단일 테이블 제약을 유지한다

근거는 이 경로의 불변식이 어디에 기대는지에 있다.

**불변식**: 영향 행 수가 목표 배치 크기를 넘으면 커밋하지 않는다.

**그것이 성립하는 이유**: 경계를 한 테이블의 기본 키로 잘랐으므로, 구간 `(from, to]`에 들어가는 그 테이블의
행 수는 경계 조회가 읽은 수(≤ 배치 크기)를 넘을 수 없다. 변경이 그 테이블의 행을 고치므로 영향 행 수도 같은 상한 안이다.

### 조인 갱신에서 왜 깨지는가

`UPDATE orders o JOIN shipments s ON s.order_id = o.id SET o.status = 'X' WHERE s.delayed`를 보자.
경계를 `orders.id`로 자르면 그 구간의 `orders` 행은 배치 크기 안이다. 여기까지는 성립한다.

문제는 **무엇을 세느냐**다.

- MySQL의 다중 테이블 UPDATE는 영향 행 수로 **실제로 바뀐 행 수**를 돌려준다. `orders` 쪽이 1:N의 1이면
  같은 `orders` 행이 여러 `shipments`와 짝지어도 한 번만 세어진다 — 이 경우는 상한 안에 든다
- 그러나 **변경 대상이 N 쪽이면** 뒤집힌다. `UPDATE shipments s JOIN orders o ... SET s.flag = 1`에서
  경계를 `orders.id`로 자르면 구간의 `orders` 100행에 매달린 `shipments`가 수천 행일 수 있다.
  영향 행 수가 배치 크기를 넘고, 불변식은 "키 열이 유일하지 않다"는 잘못된 진단을 내며 멈춘다
- 경계를 `shipments`의 키로 바꾸면 그 문제는 사라지지만, 그때는 **어느 테이블의 키로 자를지 판정**해야 한다.
  그 판정은 문장 해석이고, 이 저장소의 원칙은 "안전을 문장 해석에 걸지 않는다"다

### 서브쿼리 갱신에서 왜 깨지는가

`UPDATE orders SET status = 'X' WHERE id IN (SELECT order_id FROM shipments WHERE delayed)`는
단일 테이블 변경이라 불변식 자체는 선다. 하지만 다른 것이 깨진다.

배치는 조건을 **배치마다 다시 평가한다.** 서브쿼리 결과가 실행 중에 바뀌면(다른 트랜잭션이 `shipments`를 고치면)
앞 배치와 뒤 배치가 다른 대상 집합을 본다. 승인 시점에 사람이 본 범위와 실제로 바뀐 범위가 달라지고,
그 차이는 어디에도 기록되지 않는다.

소량 경로는 이 문제가 없다. 한 트랜잭션 안에서 사본을 잡고 대조하므로 그 사이 바뀐 것이 있으면 커밋하지 않는다.
**배치로 쪼개는 순간 "한 시점의 스냅샷"이라는 성질을 잃는다.** 단일 테이블 조건도 같은 성질을 잃지만,
그 조건은 대상 테이블 자신의 열이라 배치가 고치는 값과 같은 트랜잭션 안에 있다. 서브쿼리는 남의 테이블이다.

### 현업 도구 대조

- **Percona `pt-archiver`** — `--source`와 `--dest`를 각각 하나만 받는다. 조인 조건은 `--where`에 서브쿼리로
  쓸 수 있지만 문서가 "청크마다 다시 평가된다"고 명시한다: https://docs.percona.com/percona-toolkit/pt-archiver.html
- **Alibaba DMS 무락 변경** — 단일 테이블의 `UPDATE`·`DELETE`만 받는다:
  https://www.alibabacloud.com/help/en/dms/user-guide/change-data-without-locking-tables
- **gh-ost** — 스키마 변경 도구라 애초에 한 테이블이다

세 도구 모두 단일 테이블이다. 배치로 쪼개는 방식과 다중 테이블이 같이 가지 않는다는 것이 이 분야의 관행이다.

### 그래서 어떻게 하나

여러 테이블을 고쳐야 하면 **티켓을 나눈다.** 각 티켓이 단일 테이블 대상이고, 순서가 필요하면 승인·실행 순서로 표현한다.
서브쿼리로 대상을 고르는 변경은 그 결과를 먼저 고정해야 한다 — 예를 들어 대상 키를 임시 테이블에 담는 티켓을
먼저 실행하고, 그 테이블을 조건으로 쓰는 티켓을 뒤에 둔다. 그러면 두 번째 티켓의 조건은 더 이상 움직이지 않는다.

이 우회는 사람이 단계를 나누는 일이라 플랫폼이 자동으로 하지 않는다. 자동으로 하려면 "무엇을 임시 테이블에 담을지"를
문장 해석으로 정해야 하고, 그것이 앞서 거부한 그 판정이다.

## 이 명세가 정하지 않은 것

- MongoDB의 대량 변경(#128). Operator 능력으로 흡수할 수 있는지부터 판정한다
- 배치 크기 자동 조정(적응형). 먼저 고정값으로 실측하고(#105: 1,000행·쉼 100ms로 충분했다) 필요가 보이면 다음에 본다

## MongoDB — 같은 실행기로 흡수할 수 있다, 단 조건이 있다 (#128 판정)

### 판정

`_id`가 **한 타입일 때만** 담을 수 있다. 타입이 섞인 컬렉션은 거부한다.

### 왜 조건이 붙는가 — 실측

MongoDB의 비교 연산자는 **타입 경계를 넘지 않는다.** BSON 값은 타입 순서(number < string < object …)로
정렬되지만 `$gt`·`$lte`는 같은 타입 안에서만 비교한다. `sample` DB에서 확인했다.

```text
컬렉션: [{_id: 1}, {_id: 2}, {_id: "a"}, {_id: "b"}]

db.bp2.find({_id: {$gt: 0, $lte: 99}})   ->  [1, 2]        문자 _id는 범위에 안 들어온다
db.bp2.find({}).sort({_id: 1}).limit(2)  ->  마지막 _id = 2
db.bp2.find({_id: {$gt: 2}})             ->  []            문자 _id를 못 잡는다
```

마지막 줄이 이 판정의 근거다. 경계 조회로 얻은 마지막 키가 숫자 `2`인데, 다음 구간 `{_id: {$gt: 2}}`가
문자 `_id`를 하나도 돌려주지 않는다. 배치는 "더 고칠 행이 없다"고 보고 정상 종료하고, **문자 `_id` 문서는
조용히 빠진다.** 누락이 생기는데 오류도 나지 않는다 — 이 경로에서 가장 피해야 하는 모양이다.

SQL 계열에는 이 문제가 없다. 기본 키 열의 타입이 하나로 고정돼 있어 비교가 전 범위를 덮는다.

| 재료 | SQL | MongoDB | 판정 |
|---|---|---|---|
| 키 범위 | `WHERE id > ? AND id <= ?` | `{_id: {$gt: .., $lte: ..}}` | 한 타입이면 성립 |
| 경계 조회 | `ORDER BY id LIMIT n` | `.sort({_id: 1}).limit(n)` | 성립 |
| 구간 변경 | `UPDATE ... WHERE` | `updateMany(filter, update)` | 성립 |
| 영향 행 수 대조 | `executeLargeUpdate()` | `modifiedCount` | 성립(실측: matched 2 / modified 2) |
| 조건 재작성 금지 | `WHERE`에 `AND` | 승인된 filter에 `$and`로 범위만 덧붙임 | 성립 |
| 타임아웃 | `setQueryTimeout` | `maxTimeMS` | 성립 |
| 복제 지연 | `SHOW REPLICA STATUS` | `replSetGetStatus` optimeDate | 기존 `ReplicationState`가 이미 읽는다 |

불변식("영향 행 수가 목표를 넘으면 커밋하지 않는다")도 그대로 옮겨진다. `modifiedCount`가 목표를 넘으면
`_id`가 유일하지 않다는 뜻이고, MongoDB에서 `_id`는 항상 유일하므로 그 상황은 조건이 예상과 다르다는 신호다.

### 그래서 실행 전 조건에 한 줄이 붙는다

**대상 컬렉션의 `_id` 타입이 하나여야 한다.** 확인 방법은 한 번의 집계다.

```javascript
db.coll.aggregate([{$group: {_id: {$type: "$_id"}, n: {$sum: 1}}}])
```

결과가 두 줄 이상이면 거부한다. 이 조회는 전체 문서를 훑으므로 큰 컬렉션에서는 비싸다 — 그래서
실행 전 조건에서 한 번만 하고, 배치마다 다시 보지 않는다.

`_id`가 `ObjectId` 하나인 컬렉션은 그냥 통과한다. 그게 기본값이고 대부분이다.

### 하지 않는 것

- `_id`가 아닌 필드로 구간을 자르는 것. 유일성이 보장되지 않아 구간이 겹칠 수 있다
- 샤딩된 컬렉션. 샤드 키와 `_id`가 다르면 범위 조회가 모든 샤드로 퍼진다(scatter-gather).
  판정에 필요한 실측을 아직 하지 않았다
